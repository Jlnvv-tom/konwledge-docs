第九章：Agent 工程化与部署

当 Agent 从原型走向生产环境，工程化部署便成为不可回避的核心命题。一个在 Demo 中表现惊艳的 Agent，放到真实业务场景中可能面临延迟抖动、成本失控、错误雪崩等一系列问题。本章围绕工程化部署的八大核心主题展开，从可观测性到容错架构，从成本优化到灰度发布，系统性地构建 Agent 生产化的知识体系。

9.1 工程化部署的核心挑战​

将 LLM-based Agent 从实验室环境迁移到生产环境，与传统的软件部署有着本质区别。传统微服务部署的核心挑战集中在吞吐量、延迟和可用性三个维度，而 Agent 部署还需要额外应对不确定性输出、长时运行任务、动态工具调用等特有难题。

第一个核心挑战是延迟不可控。Agent 的响应时间不是固定的，它取决于 LLM 的推理时间、工具调用的执行时间、以及推理链路的深度。一个简单的问答可能在 2 秒内完成，而一个需要多步推理和工具调用的复杂任务可能耗时 30 秒甚至更久。这种延迟的巨大方差使得传统的超时设置和负载均衡策略难以直接套用。

第二个挑战是成本与用量的不可预测性。传统服务的成本主要来自计算资源（CPU、内存、带宽），而 Agent 的成本结构中，LLM API 调用费用往往占据主导地位。一次复杂的推理任务可能消耗数万 Token，如果遇到 Prompt 膨胀或工具调用循环，成本可能呈指数级增长。

第三个挑战是状态管理的复杂性。Agent 往往是有状态的，需要维护对话历史、工具调用上下文、中间推理结果等。在多实例部署场景下，如何保证状态一致性、如何处理会话亲和性（Session Affinity），都是需要精心设计的问题。

第四个挑战是质量评估的困难。传统服务可以通过断言式测试验证正确性，而 Agent 的输出具有不确定性和多样性，很难用简单的 pass/fail 来评判。这要求部署体系内建质量监控机制，持续评估 Agent 输出的质量。

从架构层面看，一个生产级 Agent 系统至少包含以下组件：API 网关层负责请求的鉴权、限流和路由；Agent 执行层负责编排推理流程；LLM 调用层封装模型交互；工具执行层提供沙箱化的工具运行环境；状态存储层维护会话和上下文；可观测性平台提供全链路的监控能力。

每个组件都需要独立考虑容错和扩展策略。例如，LLM 调用层需要实现多模型 Failover 机制，当主模型不可用时自动切换到备用模型；工具执行层需要资源隔离，防止某个工具调用的异常影响到其他请求。

工程化部署不是一次性工作，而是一个持续迭代的过程。团队需要建立从开发、测试、预发布到生产的完整流水线，每个阶段都有对应的质量门禁和验证标准。

9.2 可观测性系统设计：日志、指标与追踪​

可观测性（Observability）是 Agent 工程化的基石。与传统微服务不同，Agent 系统的可观测性需要额外覆盖推理过程、工具调用链路、Token 消耗等维度。一个完善的可观测性系统由三大支柱构成：日志（Logging）、指标（Metrics）和分布式追踪（Tracing）。

日志系统需要记录 Agent 运行过程中的关键事件。与传统的结构化日志不同，Agent 日志需要额外包含推理相关的上下文信息，例如当前推理步骤、使用的 Prompt 模板、LLM 响应的元数据等。

在技术选型上，日志可以采用 ELK (Elasticsearch, Logstash, Kibana) 栈或 Loki + Grafana 组合；指标推荐使用 Prometheus + Grafana；分布式追踪可以使用 OpenTelemetry 标准，后端接入 Jaeger 或 Tempo。

对于 Agent 系统特有的可观测性需求，还需要关注以下几个维度。首先是推理链路的可视化，需要将 Agent 的思维链（Chain of Thought, CoT）过程以可读的方式呈现，便于调试和优化。其次是 Prompt 版本与输出质量的关联分析，帮助理解不同 Prompt 版本对 Agent 表现的影响。最后是工具调用模式的统计分析，识别高频工具、低效调用等问题。

告警策略需要分层设计。第一层是基础设施告警，如 CPU 使用率、内存使用率、磁盘空间等；第二层是应用层告警，如错误率飙升、延迟异常等；第三层是业务层告警，如 Token 消耗异常增长、用户满意度下降等。每层告警应设置不同的通知渠道和响应优先级。

9.3 成本优化策略：从模型分级到缓存​

Agent 系统的运行成本主要由 LLM API 调用费用构成。在缺乏优化策略的情况下，一个面向消费者的 Agent 应用，每月的 LLM 调用费用可能轻易达到数万美元。成本优化不是事后补丁，而应在架构设计阶段就纳入考量。

模型分级路由是最直接有效的成本优化手段。核心思路是根据请求的复杂度，将任务路由到不同成本级别的模型。简单任务使用小模型，复杂任务才调用大模型。

任务类型示例推荐模型层级相对成本
意图分类判断用户是咨询还是投诉小模型 (8B)1x
信息抽取从文本中提取实体小模型 (8B)1x
简单问答FAQ 知识库检索回答中模型 (70B)5x
多步推理复杂问题分析+工具调用大模型 (GPT-4级)20x
内容生成长文写作、代码生成大模型 (GPT-4级)20x
结果校验检查输出是否准确小模型 (8B)1x

路由决策本身可以由一个轻量级分类器完成。这个分类器可以基于规则（如关键词匹配）、基于传统 ML 模型（如 FastText）、或使用小模型进行快速分类。关键是路由决策本身不能引入过多延迟和成本。

缓存策略是另一个重要的成本优化方向。Agent 系统中存在大量可缓存的中间结果。第一层是 Prompt 级缓存，对于完全相同的 Prompt 输入，可以直接返回缓存的响应。OpenAI 和 Anthropic 等模型提供商已经原生支持 Prompt Caching，对于前缀相同的 Prompt 自动给予折扣。

第二层是语义缓存，通过 Embedding 相似度匹配，对语义相近的请求复用历史响应。语义缓存需要设置合理的相似度阈值，过高导致命中率低，过低可能导致返回不相关的结果。

第三层是工具结果缓存。很多工具调用的结果在短时间内不会变化，例如查询天气、搜索文档等。通过对工具调用结果进行 TTL (Time to Live, 生存时间) 缓存，可以避免重复调用。

import hashlib
from functools import lru_cache

class AgentCache:
    def __init__(self, ttl_seconds=3600):
        self.ttl = ttl_seconds
        self._cache = {}

    def _key(self, prompt: str, model: str) -> str:
        content = f"{model}:{prompt}"
        return hashlib.sha256(content.encode()).hexdigest()

    def get(self, prompt: str, model: str):
        key = self._key(prompt, model)
        entry = self._cache.get(key)
        if entry and time.time() - entry["ts"] < self.ttl:
            return entry["response"]
        return None

    def set(self, prompt: str, model: str, response: str):
        key = self._key(prompt, model)
        self._cache[key] = {"response": response, "ts": time.time()}

Prompt 优化是成本控制的另一个维度。Prompt 的长度直接影响 Token 消耗，过长的 Prompt 不仅增加成本，还可能降低模型表现。优化手段包括：压缩系统提示词、精简 Few-shot 示例、使用更紧凑的输出格式要求等。

一个实际案例：某 Agent 应用的系统 Prompt 从 3000 Token 优化到 1200 Token，每次请求节省 1800 Token。按日均 100 万次请求计算，每天节省约 18 亿 Token，月度成本下降显著。

批量处理（Batch Processing）也是有效的成本优化手段。对于非实时性要求的任务，可以采用批量推理接口。OpenAI 的 Batch API 提供 50% 的价格折扣，对于可以容忍 24 小时延迟的任务非常合适。

Token 预算控制是防止成本失控的最后一道防线。系统应为每个会话设置 Token 预算上限，当消耗接近阈值时触发告警，超出阈值时拒绝或降级处理。这可以有效防止因 Prompt 膨胀或工具调用循环导致的成本异常。

9.4 流式输出设计：SSE 与 WebSocket​

Agent 的推理过程通常需要数秒到数十秒，如果采用传统的请求-响应模式，用户需要等待全部推理完成后才能看到结果，体验较差。流式输出可以让用户逐步看到 Agent 的思考过程和中间结果，显著提升用户体验。

流式输出有两种主流技术方案：SSE (Server-Sent Events, 服务器推送事件) 和 WebSocket。

SSE 是基于 HTTP 的单向推送协议。服务端通过长连接持续向客户端推送数据，客户端只能接收不能发送。SSE 的优势在于实现简单、基于标准 HTTP 协议、天然支持断线重连。对于 Agent 场景，用户请求后只需接收推理结果，不需要在推理过程中发送额外数据，SSE 是理想选择。

WebSocket 是全双工通信协议，客户端和服务端可以互相发送消息。WebSocket 适用于需要实时交互的场景，例如用户在 Agent 推理过程中需要补充信息或调整方向。

以下是 SSE 流式输出的服务端实现示例：

from fastapi import FastAPI
from fastapi.responses import StreamingResponse
import json, asyncio

app = FastAPI()

async def agent_stream(query: str):
    # 发送推理开始事件
    yield f"data: {json.dumps({'type': 'start', 'query': query})}\n\n"
    
    # 模拟多步推理
    steps = ["分析问题", "检索知识库", "生成答案"]
    for i, step in enumerate(steps):
        await asyncio.sleep(1)  # 模拟推理耗时
        yield f"data: {json.dumps({'type': 'step', 'index': i, 'content': step})}\n\n"
    
    # 发送最终结果
    yield f"data: {json.dumps({'type': 'complete', 'answer': '推理完成'})}\n\n"

@app.get("/agent/stream")
async def stream_agent(query: str):
    return StreamingResponse(
        agent_stream(query),
        media_type="text/event-stream",
        headers={
            "Cache-Control": "no-cache",
            "Connection": "keep-alive",
            "X-Accel-Buffering": "no",  # 禁用 Nginx 缓冲
        }
    )

客户端实现同样简洁：

const eventSource = new EventSource('/agent/stream?query=你好');

eventSource.onmessage = function(event) {
    const data = JSON.parse(event.data);
    if (data.type === 'step') {
        console.log(`步骤 ${data.index}: ${data.content}`);
    } else if (data.type === 'complete') {
        console.log(`结果: ${data.answer}`);
        eventSource.close();
    }
};

eventSource.onerror = function() {
    console.error('连接异常，自动重连中...');
    // EventSource 会自动重连
};

在实际部署中，流式输出需要特别注意几个工程细节。首先是 Nginx 等反向代理的缓冲配置。默认情况下 Nginx 会缓冲后端响应，这会导致 SSE 数据无法实时推送。需要在响应头中设置 X-Accel-Buffering: no，或在 Nginx 配置中关闭 proxy_buffering。

其次是连接管理。SSE 连接是长连接，每个连接占用一个服务器连接槽。需要设置合理的超时时间和最大连接数限制，防止连接泄漏导致资源耗尽。

最后是断线重连的状态恢复。SSE 标准支持 Last-Event-ID 头，客户端重连时会携带最后收到的事件 ID，服务端可以据此恢复推送状态。这对于网络不稳定的移动端场景尤为重要。

在 Agent 流式输出中，事件类型的设计也很关键。一个完善的事件协议应包含以下类型：start（推理开始）、thinking（思考过程）、tool_call（工具调用）、tool_result（工具返回）、partial_answer（部分答案）、complete（完成）、error（错误）。不同事件类型携带不同的数据字段，客户端据此渲染不同的 UI 组件。

9.5 人在回路审批机制​

Agent 自主执行能力的提升带来了新的风险控制需求。在涉及资金操作、数据修改、外部通信等高风险场景中，完全自主的 Agent 可能造成不可逆的后果。HITL (Human-in-the-Loop, 人在回路) 机制通过在关键决策点引入人工审批，平衡了自动化效率和操作安全性。

审批机制的设计需要明确哪些操作需要人工审批。通常可以根据风险等级将 Agent 操作分为三类：低风险操作（如信息查询、只读操作）无需审批直接执行；中风险操作（如发送邮件、更新数据）需要通知人工但可以先行执行；高风险操作（如资金转账、删除数据、发布内容）必须等待人工审批后才能执行。

└──────────────────────────────────────────────────────┘

审批界面的设计直接影响审批效率和质量。一个优秀的审批界面应包含以下信息：Agent 的推理过程（为什么要做这个操作）、操作的具体内容（操作目标、参数、预期影响）、风险评级和依据、历史类似操作的审批记录。

审批机制可以进一步细分为同步审批和异步审批。同步审批要求 Agent 暂停推理流程，等待审批结果后继续。这种方式适用于需要审批结果来决定后续推理方向的场景。异步审批允许 Agent 继续处理其他不依赖该审批的任务，审批结果到达后再执行相应操作。

以下是同步审批的代码架构示例：

from enum import Enum
from dataclasses import dataclass
from typing import Optional

class RiskLevel(Enum):
    LOW = "low"
    MEDIUM = "medium"
    HIGH = "high"

class ApprovalStatus(Enum):
    PENDING = "pending"
    APPROVED = "approved"
    REJECTED = "rejected"

@dataclass
class ApprovalRequest:
    request_id: str
    agent_id: str
    action: str
    params: dict
    risk_level: RiskLevel
    reasoning: str
    status: ApprovalStatus = ApprovalStatus.PENDING

class ApprovalManager:
    async def request_approval(
        self, action: str, params: dict, 
        reasoning: str, risk: RiskLevel
    ) -> bool:
        if risk == RiskLevel.LOW:
            return True  # 低风险直接通过
        
        req = ApprovalRequest(
            request_id=generate_id(),
            agent_id=self.agent_id,
            action=action, params=params,
            risk_level=risk, reasoning=reasoning
        )
        await self.queue.push(req)
        
        # 等待审批结果（带超时）
        result = await self.wait_for_approval(
            req.request_id, timeout=300
        )
        return result == ApprovalStatus.APPROVED

审批机制还需要考虑超时处理策略。当审批未在规定时间内完成时，系统可以采取以下策略之一：自动拒绝（保守策略，适用于高风险操作）、自动批准（激进策略，仅适用于可逆操作）、升级通知（通知更高级别的人员）、转入异步队列（不阻塞当前流程）。

审批日志是合规审计的重要组成部分。系统应记录每次审批的完整上下文，包括审批请求内容、审批人、审批时间、审批结果、以及审批后的执行结果。这些日志不仅用于事后追溯，还可以用于分析审批效率和优化风险评级模型。

在实际应用中，审批机制还可以结合规则引擎实现智能路由。例如，金额低于 100 元的转账可以自动审批，高于 100 元的需要主管审批，高于 10000 元的需要双重审批。规则引擎使得审批策略可以灵活调整，无需修改代码。

9.6 错误恢复与容错架构​

Agent 系统的容错设计比传统服务更为复杂。传统服务的错误通常是明确的（如 HTTP 502、数据库连接超时），而 Agent 系统还可能遇到 LLM 输出格式错误、工具调用失败、推理陷入循环等非传统错误。

容错架构的第一层是重试机制。对于临时性错误（如网络抖动、API 限流），重试是最简单有效的恢复手段。重试策略需要考虑以下因素：重试次数限制、重试间隔（推荐指数退避）、可重试的错误类型、重试时的上下文处理。

import asyncio
from typing import TypeVar, Callable

T = TypeVar("T")

class RetryConfig:
    def __init__(
        self, max_attempts: int = 3,
        base_delay: float = 1.0,
        max_delay: float = 60.0,
        exponential: bool = True
    ):
        self.max_attempts = max_attempts
        self.base_delay = base_delay
        self.max_delay = max_delay
        self.exponential = exponential

async def with_retry(
    func: Callable, config: RetryConfig, 
    *args, **kwargs
) -> T:
    last_error = None
    for attempt in range(config.max_attempts):
        try:
            return await func(*args, **kwargs)
        except RetryableError as e:
            last_error = e
            if attempt < config.max_attempts - 1:
                delay = config.base_delay * (
                    2 ** attempt if config.exponential else 1
                )
                delay = min(delay, config.max_delay)
                await asyncio.sleep(delay)
    raise last_error

第二层是超时控制。Agent 系统中需要多层级的超时设置：单个 LLM 调用的超时、单个工具调用的超时、单步推理的超时、整个请求的超时。超时设置应遵循从内到外递增的原则，外层超时大于内层超时之和。

第三层是熔断器（Circuit Breaker）模式。当某个组件（如某个 LLM 提供商）连续失败达到阈值时，熔断器触发，后续请求直接快速失败而不再尝试调用。经过一段冷却时间后，熔断器进入半开状态，允许少量请求试探性调用，如果成功则恢复正常状态。

第四层是降级策略。当系统无法提供完整服务时，通过降级提供部分功能而非完全不可用。常见的降级策略包括：从大模型降级到小模型（牺牲质量但保证可用）、从多步推理降级为单步直接回答、从工具调用降级为纯文本回答、从个性化回答降级为通用模板回答。

第五层是死信队列（Dead Letter Queue, DLQ）。对于无法成功处理的请求，将其转入死信队列，由人工或离线流程处理。这避免了失败请求堵塞正常流程，同时保证不丢失任何请求。

┌─────────────────────────────────────────────────┐
│            Agent 容错架构分层模型                   │
├─────────────────────────────────────────────────┤
│                                                 │
│  Layer 5: 死信队列 (DLQ)                         │
│  └─ 无法处理的请求转人工                          │
│                                                 │
│  Layer 4: 降级策略                               │
│  └─ 大模型→小模型, 多步→单步, 工具→纯文本          │
│                                                 │
│  Layer 3: 熔断器                                 │
│  └─ 连续失败时快速失败, 冷却后试探恢复              │
│                                                 │
│  Layer 2: 超时控制                               │
│  └─ 多层级超时: 调用级/步骤级/请求级               │
│                                                 │
│  Layer 1: 重试机制                               │
│  └─ 指数退避重试, 可重试错误识别                   │
│                                                 │
└─────────────────────────────────────────────────┘

推理循环检测是 Agent 特有的容错需求。Agent 在执行多步推理时，可能陷入"调用工具 A 得到结果，再调用工具 B，又回到调用工具 A"的循环。检测机制可以基于工具调用序列的模式匹配，当检测到重复模式时强制终止推理并返回当前最佳结果。

LLM 输出校验也是不可忽视的容错环节。LLM 可能返回不符合预期格式的输出，例如要求 JSON 格式但返回了包含 Markdown 代码块的文本。系统需要健壮的输出解析器，能够处理各种边界情况，并在解析失败时触发重试或降级。

状态快照（State Snapshot）机制用于长时运行任务的恢复。Agent 的推理过程可能耗时较长，如果中途因故障中断，从头开始重试代价很大。通过定期保存推理状态快照，可以在故障后从最近的快照恢复，减少重复计算。

9.7 版本管理与灰度发布​

Agent 系统的版本管理比传统软件更为复杂，因为 Agent 的行为不仅由代码决定，还受到 Prompt、模型版本、工具配置等多种因素的影响。一个完整的版本管理策略需要覆盖所有这些维度。

版本管理的第一个维度是 Prompt 版本控制。Prompt 是 Agent 行为的核心定义，微小的措辞变化可能导致行为显著变化。Prompt 应像代码一样纳入版本控制，每次修改都记录变更说明、修改原因、预期影响。推荐使用结构化的 Prompt 模板，将变量部分与固定部分分离。

第二个维度是模型版本管理。LLM 提供商会定期更新模型版本，同一模型名称的不同版本可能表现不同。系统应明确记录每个 Agent 使用的模型版本，并在模型更新前进行充分的回归测试。对于 OpenAI 等提供商，可以指定模型版本（如 gpt-4-0613）而非使用默认最新版本。

第三个维度是工具配置版本管理。工具的接口定义、参数格式、行为逻辑都可能变化。每次工具更新都应记录版本号，Agent 调用工具时应指定工具版本，避免因工具静默更新导致行为异常。

灰度发布（Canary Release）是降低发布风险的关键手段。灰度发布的核心思想是将新版本先发布给一小部分用户，观察指标正常后逐步扩大范围。

灰度发布流程:

  ┌─────────────┐
  │ 新版本构建完成 │
  └──────┬──────┘
         │
  ┌──────▼──────┐
  │ 影子流量验证  │  (不发真实流量, 复制线上流量回放)
  └──────┬──────┘
         │ 通过
  ┌──────▼──────┐
  │ 5% 流量灰度  │  (监控: 错误率, 延迟, 成本, 质量)
  └──────┬──────┘
         │ 指标正常, 持续 30 分钟
  ┌──────▼──────┐
  │ 20% 流量灰度 │
  └──────┬──────┘
         │ 指标正常, 持续 1 小时
  ┌──────▼──────┐
  │ 50% 流量灰度 │
  └──────┬──────┘
         │ 指标正常, 持续 2 小时
  ┌──────▼──────┐
  │ 100% 全量发布 │
  └──────┬──────┘
         │
  ┌──────▼──────┐
  │ 发布完成, 保留 │
  │ 旧版本 24h   │  (可快速回滚)
  └─────────────┘

灰度发布的流量分配可以基于多种策略：基于用户 ID 的哈希分配（保证同一用户始终访问同一版本）、基于请求特征的分配（如按地区、设备类型）、基于时间的分配（如先在低峰时段灰度）。推荐基于用户 ID 哈希的分配方式，避免用户在不同版本间切换导致体验不一致。

灰度期间的监控指标应包括技术指标和业务指标两个维度。技术指标包括错误率、延迟、资源使用率等；业务指标包括用户满意度（如点赞/踩的比例）、任务完成率、Token 消耗等。任何指标异常都应触发自动回滚。

A/B 测试是灰度发布的延伸应用。通过同时运行多个版本，将流量分配到不同版本，对比各版本在关键指标上的表现，以数据驱动的方式选择最优版本。A/B 测试需要注意统计显著性，避免因样本量不足导致错误结论。

回滚机制是版本管理的安全网。系统应支持一键回滚到任意历史版本，回滚操作应在秒级完成。为实现快速回滚，可以采用蓝绿部署（Blue-Green Deployment）策略，始终维护一个备用版本环境，切换流量即可完成回滚。

版本管理的最佳实践还包括变更审批流程。Prompt 变更、模型升级、工具更新等都应经过代码审查和测试验证。可以设置自动化的质量门禁，例如新版本必须通过一定数量的测试用例才能进入灰度阶段。

9.8 多租户架构与部署拓扑​

当 Agent 服务面向多个客户（租户）提供时，多租户架构成为必须解决的设计问题。多租户架构的核心挑战是在资源隔离、数据安全、性能保障和成本效率之间找到平衡点。

多租户架构主要有三种模式，各有优劣：

隔离模式资源隔离数据安全成本适用场景
共享一切 (Shared-All)弱低最低免费版/小型租户
共享计算, 独立存储中中中等中型租户/SaaS 标准
完全独立 (Single-Tenant)强高最高企业版/合规要求高

共享一切模式下，所有租户共享同一套 Agent 实例、数据库和存储。通过在数据模型中添加租户 ID 字段实现逻辑隔离。这种模式成本最低，但存在数据泄露风险和资源争抢问题。适用于免费或低价值用户。

共享计算、独立存储模式下，Agent 计算资源共享，但每个租户的数据存储在独立的数据库 Schema 或独立的数据桶中。这种模式在成本和安全性之间取得了较好的平衡，是大多数 SaaS 产品的选择。

完全独立模式下，每个租户拥有独立的 Agent 实例、数据库和存储。这种模式提供最强的隔离和安全保障，但成本最高。适用于对数据安全有严格要求的企业客户，如金融、医疗行业。

Agent 系统的多租户设计还需要考虑以下特殊问题。首先是 Prompt 的租户隔离。不同租户可能使用不同的系统 Prompt、Few-shot 示例、工具配置。系统需要支持基于租户的配置管理，确保每个租户的 Agent 行为符合其业务需求。

其次是模型使用的租户差异化。不同租户可能使用不同级别的模型，付费用户使用大模型，免费用户使用小模型。路由层需要根据租户身份选择对应的模型。

部署拓扑的选择需要综合考虑延迟要求、数据主权、合规要求等因素。对于全球用户的服务，可以采用多区域部署策略。每个区域部署独立的 Agent 集群，用户请求路由到最近的区域，降低网络延迟。

数据主权是跨国部署必须考虑的问题。某些国家/地区的法规要求数据不得离开本国/本地区。例如，欧盟的 GDPR (General Data Protection Regulation, 通用数据保护条例) 对个人数据的跨境传输有严格限制。多区域部署需要确保用户数据在对应区域内处理和存储。

边缘部署是将 Agent 的部分能力下沉到离用户更近的位置。例如，将意图识别和简单问答放在边缘节点处理，将复杂推理回源到中心节点。这种架构可以显著降低简单请求的延迟，同时保证复杂请求的推理质量。

容量规划是多租户部署的重要环节。Agent 系统的容量规划与传统服务不同，因为 LLM API 调用的并发限制可能成为瓶颈。需要根据 LLM 提供商的并发限制（如 OpenAI 的 RPM/TPM 限制）来计算系统能支持的最大并发请求数，并据此规划 Agent 实例数量。

弹性伸缩策略也需要特别设计。Agent 实例的启动时间可能较长（需要加载模型配置、初始化工具等），伸缩反应速度不如传统服务。可以采用预测性伸缩策略，根据历史流量模式提前调整实例数量，而非完全依赖实时指标触发的反应式伸缩。

最后，多租户系统的可观测性需要支持租户维度的指标聚合。每个租户应有独立的监控看板，展示该租户的请求量、延迟分布、错误率、Token 消耗、成本统计等。运营团队需要全局视角的看板，对比各租户的资源使用情况，识别异常占用和潜在问题。
