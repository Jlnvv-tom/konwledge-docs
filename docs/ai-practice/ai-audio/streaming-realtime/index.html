第 8 章：流式与实时语音模型

系列文章：《语音与音乐的机器之魂》 GPT-4o 让实时语音对话成为现实。本章解析流式语音处理的技术挑战、全双工交互的实现方案，以及延迟优化的工程实践。

1. 为什么需要流式​

传统语音处理是"离线"的——先录完整段音频，再处理。但许多场景需要实时性：

  • 智能助手：用户说完即回应，不能等几秒
  • 同声传译：边说边翻译
  • 直播字幕：实时生成字幕
  • 游戏语音：NPC 实时对话
  • 客服系统：低延迟交互

核心指标：响应延迟

延迟用户感受
< 200ms即时（人类对话级）
200-500ms流畅
500-1000ms可感知延迟
1-2s明显卡顿
> 2s难以接受

2. 流式 ASR​

2.1 chunk-based 处理​

将音频流分成小块处理：

音频流 → [chunk 1 (300ms)] → [chunk 2] → [chunk 3] → ...
              ↓                ↓            ↓
          部分结果            更新结果     最终结果
          "你"              "你好"       "你好世界"

关键问题：chunk 大小如何选择？

chunk 大小延迟上下文准确率
100ms极低少低
300ms低中中
500ms中多高
1000ms高多最高

2.2 流式架构​

RNN-T（天然流式）​

音频帧(实时) → 编码器 → ┐
                         → Joint Network → token
上一个token → 预测网络 ─┘

RNN-T 天然支持因果推理，是工业界流式 ASR 的首选。

Chunk-Attention​

音频流 → [chunk + 左侧上下文] → 注意力(限窗) → 输出
  • 限制注意力窗口到最近 N 帧
  • 左侧上下文提供历史信息
  • 不使用右侧（未来）信息

因果卷积​

# 普通卷积：使用前后帧
conv = Conv1d(padding=(kernel_size-1)//2)  # 双侧 padding

# 因果卷积：只使用过去帧
causal_conv = Conv1d(padding=kernel_size-1)  # 左侧 padding
output = causal_conv(x)[:, :, :-(kernel_size-1)]  # 丢弃右侧

2.3 VAD 与端点检测​

VAD（Voice Activity Detection）：检测有无语音

  • 基于 RNN/Transformer 的 VAD
  • 能量 + 过零率的简单 VAD

Endpointing：判断一句话是否结束

  • 静音持续 N ms → 认为说完
  • 太短 → 误触发；太长 → 延迟大
  • 通常设为 500-800ms

3. 流式 TTS​

3.1 挑战​

流式 TTS 比流式 ASR 更难：

  • TTS 需要知道句子结构才能正确分韵律
  • 首字延迟要小
  • 生成速度必须快于播放速度
  • 句子边界需要准确判断

3.2 解决方案​

句子级流式​

ASR: "你好世界。今天天气很好。" → 等到第一个句号
TTS: 合成"你好世界" → 播放同时等待下一句
  • 最简单的方案
  • 延迟 = ASR 延迟 + 句子检测延迟
  • 韵律最好（完整句子信息）

chunk-level 合成​

文本 → 按短语/分句切分 → 逐 chunk 合成 → 交叉淡入淡出拼接
  • 延迟更低
  • chunk 边界可能有韵律不连贯
  • 需要精细的拼接算法

token 级流式​

LLM-based TTS 天然支持：

LLM 逐 token 生成 → 每 N 个 token 解码一小段音频 → 流式播放
  • 延迟最低
  • 但韵律可能受影响（看不到完整句子）

3.3 流式声码器​

传统声码器需要完整 Mel 频谱，流式声码器需要逐帧或逐 chunk 生成：

Mel帧(1帧=11.6ms) → 声码器 → 音频片段(256采样点)
     ↑ 逐帧输入               ↓ 逐帧输出

HiFi-GAN 可以改造为流式：用因果卷积 + 状态缓存。

4. 全双工语音交互​

4.1 什么是全双工​

半双工：对讲机模式——一人说一人听

用户说话 → [等用户说完] → AI 处理 → AI 说话 → [等AI说完] → ...

全双工：电话模式——双方可同时说

用户说话 ←→ AI 同时说话
（用户可随时打断 AI）

GPT-4o 代表了 AI 语音交互的全双工新时代。

4.2 全双工的技术挑战​

  1. 回声消除：AI 的声音不应被麦克风重新采集
  2. 打断处理：用户打断时，AI 需立即停止
  3. 端点检测：在 AI 说话时检测用户是否在说话
  4. 对话状态管理：听、想、说 三种状态的切换

4.3 全双工架构​

                    ┌─── ASR (流式) ────→ LLM (流式) ────→ TTS (流式) ───┐
                    │                                                      │
麦克风 ──→ AEC ──→ ┤                                                      ↓
                    │                                                  扬声器
                    └─── VAD/打断检测 ──→ 停止 TTS ←──────────────────────┘

AEC（Acoustic Echo Cancellation）：

  • 自适应滤波器消除扬声器到麦克风的回声
  • 使 AI 能在说话时"听到"用户是否打断了它

打断处理：

AI 正在说话 → VAD 检测到用户说话 → 停止 TTS 生成 → 切换到听模式

4.4 通信协议​

协议延迟场景
WebSocket50-200msWeb 应用
WebRTC20-100ms浏览器原生
gRPC10-50ms服务端间
UDP + 自定义< 50ms极低延迟

5. 延迟优化​

5.1 端到端延迟分解​

用户开口 → ASR(200-500ms) → LLM首token(200-1000ms) → TTS(100-300ms) → 网络(50-200ms)
                                                                    ↓
                                                            总计: 550-2000ms
                                                            目标: < 800ms

5.2 各组件优化​

ASR 优化​

  • 更小的 chunk（300ms）
  • 流式 RNN-T
  • 量化到 INT8

LLM 优化​

  • KV Cache：缓存注意力键值，避免重复计算
  • 投机解码：小模型起草，大模型并行验证
  • 流式输出：生成第一个 token 即可开始 TTS
  • 更小的模型：7B 优于 70B（但质量略低）

TTS 优化​

  • 流式 TTS（句子级或 chunk 级）
  • 非自回归声码器（HiFi-GAN）
  • 预热模型，避免冷启动

网络优化​

  • 边缘部署（就近推理）
  • UDP 替代 TCP
  • 音频压缩（Opus 编码）

5.3 级联 vs 统一模型​

级联方案（ASR → LLM → TTS）：

  • 模块独立优化
  • 灵活替换
  • 但累积延迟高

统一模型（如 GPT-4o）：

  • 语音 → 语音，无中间文本
  • 延迟更低
  • 保留非语言信息（语气、情感）
  • 但训练和部署复杂

5.4 实际延迟参考​

系统延迟方案
传统智能音箱1500-3000ms级联
优化级联系统800-1200ms流式级联
GPT-4o~300ms原生多模态
人类对话~200ms—

6. 实践：搭建流式语音对话系统​

6.1 架构设计​

浏览器/WebRTC
    ↓ (音频流)
WebSocket Gateway
    ↓
流式 ASR (FunASR/Whisper-streaming)
    ↓ (文本流)
LLM (流式生成)
    ↓ (文本流)
流式 TTS (CosyVoice/Edge-TTS)
    ↓ (音频流)
WebSocket Gateway
    ↓
浏览器播放

6.2 关键代码片段​

# WebSocket 服务端伪代码
async def voice_chat(websocket):
    asr = StreamingASR()
    llm = StreamingLLM()
    tts = StreamingTTS()
    
    async for audio_chunk in websocket:
        # 1. ASR 流式识别
        text = asr.process(audio_chunk)
        if not text:
            continue
        
        # 2. LLM 流式生成
        async for token in llm.generate_stream(text):
            # 3. TTS 流式合成
            audio = tts.synthesize_stream(token)
            if audio:
                await websocket.send(audio)
            
            # 检查用户是否打断
            if check_interruption(websocket):
                tts.stop()
                break

7. 本章小结​

实时语音交互是 AI 从"工具"走向"伙伴"的关键门槛：

  1. 流式 ASR：chunk-based + 因果推理 + VAD
  2. 流式 TTS：句子级/chunk级/token级，各有取舍
  3. 全双工：AEC + 打断检测 + 状态管理
  4. 延迟优化：每个组件都要优化，目标 < 800ms

GPT-4o 证明了原生多模态的可行性，但级联方案在实际部署中仍占主导——灵活性、可控性和成本都是优势。

未来趋势是统一语音模型——一个模型同时处理理解与生成，实现真正的人类级对话体验。
