# 第2章 Chrome 多进程架构详解

> 你每天打开几十个标签页，Chrome 却能做到一个页面崩溃其他页面安然无恙。这背后的秘密，就藏在一个叫「多进程架构」的设计里。

我是怕浪猫，一个喜欢把浏览器拆开看的技术博主。上期我们讲了浏览器的演进史和 Chrome 的诞生，今天进入第 2 章，我们拆解 Chrome 的多进程架构。这一章会讲清楚 Chrome 里到底有哪些进程，它们各自干什么活，进程之间怎么通信，以及站点隔离是怎么从架构层面保护你的安全的。

## 2.1 进程模型总览

Chrome 的多进程架构不是一个简单的「一个标签页一个进程」模型，而是一个精细分工的进程体系。每个进程都有明确的职责边界，通过定义好的接口进行协作。

当你打开 Chrome 浏览器，实际上启动了一组协同工作的进程。我们可以用 Chrome 自带的任务管理器（Shift+Esc 或 菜单 > 更多工具 > 任务管理器）看到所有进程。

Chrome 的进程体系概览：

```
Chrome 进程架构总览
┌──────────────────────────────────────────┐
│           Browser 进程（主进程）            │
│  UI 界面 / 标签页管理 / 用户输入            │
└────────┬─────────────────────────────────┘
         │ Mojo IPC
    ┌────┼────────────────────────┬────────┐
    │    │                        │        │
┌───┴──┐ ┌───┴────┐ ┌──────────┐ ┌───┴──┐ │
│Renderer│ │Renderer│ │Renderer  │ │ GPU  │ │
│ 进程 A │ │ 进程 B │ │ 进程 C   │ │ 进程 │ │
│(标签1)│ │(标签2) │ │(iframe)  │ │      │ │
└───────┘ └────────┘ └──────────┘ └──────┘ │
                                         │
┌─────────────┐ ┌──────────┐ ┌──────────┴┘
│ Network 进程 │ │Utility   │ │ Storage   │
│ 网络请求     │ │ 进程     │ │ 进程      │
└─────────────┘ └──────────┘ └───────────┘
```

### 2.1.1 浏览器主进程（Browser Process）

Browser 进程是 Chrome 的「指挥中心」，也是用户启动 Chrome 时第一个创建的进程。它负责所有与用户直接交互的工作。

Browser 进程的核心职责：

| 职责 | 说明 |
|------|------|
| UI 渲染 | 地址栏、标签栏、书签栏、工具栏等浏览器界面的绘制 |
| 标签页管理 | 创建、切换、关闭标签页，管理标签页的生命周期 |
| 用户输入处理 | 鼠标点击、键盘输入、触摸手势等输入事件的路由 |
| 导航管理 | 处理地址栏输入、链接点击，协调网络请求和渲染进程 |
| 权限管理 | 位置、通知、摄像头等权限的授权弹窗和管理 |
| 书签和历史 | 书签管理器、浏览历史的读写 |
| 进程协调 | 创建和销毁渲染进程，管理进程间的任务分配 |

Browser 进程内部也分为多个线程，主要包括：

```
Browser 进程内部线程模型
┌─────────────────────────────────────────┐
│              Browser 进程                │
│  ┌────────────┐  ┌────────────┐         │
│  │  UI 线程    │  │ IO 线程    │         │
│  │ 界面绘制    │  │ IPC 通信   │         │
│  └────────────┘  └────────────┘         │
│  ┌────────────┐  ┌────────────┐         │
│  │ File 线程   │  │ DB 线程    │         │
│  │ 文件操作    │  │ 数据库操作 │         │
│  └────────────┘  └────────────┘         │
│  ┌────────────┐  ┌────────────┐         │
│  │ Cache 线程  │  │ Process    │         │
│  │ 缓存管理    │  │ Launcher   │         │
│  │            │  │ 进程启动   │         │
│  └────────────┘  └────────────┘         │
└─────────────────────────────────────────┘
```

UI 线程是最重要的线程，所有用户可见的界面更新都在 UI 线程上完成。IO 线程负责处理所有 IPC（Inter-Process Communication，进程间通信）消息，它是 Browser 进程与其他进程通信的枢纽。

> Browser 进程就像公司的前台：它不干具体的活，但所有的协调、调度、用户接待都由它负责。没有它，其他进程就各自为政了。

### 2.1.2 渲染进程（Renderer Process）

渲染进程是 Chrome 中数量最多的进程类型，它负责所有 Web 内容的渲染工作。当你打开一个网页，HTML 解析、CSS 计算、布局、绘制、JavaScript 执行，全部在渲染进程中完成。

渲染进程的核心职责：

| 职责 | 说明 |
|------|------|
| HTML 解析 | 将 HTML 文本转换为 DOM（Document Object Model，文档对象模型）树 |
| CSS 解析 | 将 CSS 文本转换为 CSSOM（CSS Object Model，CSS 对象模型） |
| 布局计算 | 计算每个元素的位置和大小 |
| 绘制 | 将布局结果转换为绘制指令 |
| JavaScript 执行 | 运行页面中的 JavaScript 代码（通过 V8 引擎） |
| 事件处理 | 处理鼠标、键盘、触摸等事件 |

渲染进程内部有一个主线程（Main Thread），这是最关键的线程。JavaScript 执行、DOM 操作、样式计算、布局、绘制几乎都在主线程上完成。这也是为什么 JavaScript 的执行会阻塞渲染：它们共享同一个线程。

渲染进程的线程模型：

```
Renderer 进程内部线程模型
┌─────────────────────────────────────────┐
│            Renderer 进程                 │
│                                         │
│  ┌──────────────────────────────────┐   │
│  │        Main Thread（主线程）       │   │
│  │  JavaScript / DOM / CSS / Layout │   │
│  │  Paint / 垃圾回收                  │   │
│  └──────────────────────────────────┘   │
│                                         │
│  ┌────────────┐  ┌──────────────────┐   │
│  │ Compositor │  │ Compositor Raster│   │
│  │ Thread     │  │ Thread           │   │
│  │ 合成线程    │  │ 光栅化线程        │   │
│  └────────────┘  └──────────────────┘   │
│                                         │
│  ┌────────────┐  ┌──────────────────┐   │
│  │ IO Thread  │  │ Worker Threads   │   │
│  │ IPC 通信    │  │ Web Worker       │   │
│  └────────────┘  └──────────────────┘   │
└─────────────────────────────────────────┘
```

主线程和合成线程的分离是 Chrome 渲染架构的关键设计。主线程负责 JavaScript、布局和绘制，合成线程负责将已绘制的内容合成到屏幕上。当页面滚动时，如果合成层已经准备好，合成线程可以直接处理滚动，不需要打扰主线程。这就是为什么 CSS transform 动画能做到 60fps 的原因。

> 渲染进程的主线程是浏览器中最繁忙的线程，没有之一。JavaScript 执行、DOM 操作、布局计算、绘制指令生成，全都在这条线程上排队。理解主线程的忙碌，就理解了前端性能优化的一半。

### 2.1.3 GPU 进程（GPU Process）

GPU 进程是 Chrome 中唯一负责与 GPU（Graphics Processing Unit，图形处理器）交互的进程。无论你打开了多少个标签页，GPU 进程只有一个。

为什么需要独立的 GPU 进程？因为 GPU 是共享资源，多个渲染进程不能直接访问 GPU。GPU 进程充当了 GPU 访问的中间人角色。

GPU 进程的核心职责：

| 职责 | 说明 |
|------|------|
| 光栅化 | 将绘制指令转换为像素数据 |
| 纹理上传 | 将光栅化结果作为纹理上传到 GPU |
| 合成输出 | 将多个合成层合并为最终画面 |
| WebGL 渲染 | 执行 WebGL（Web Graphics Library）绘图命令 |
| Canvas 加速 | 硬件加速的 Canvas 2D 绘制 |

GPU 进程接收来自多个渲染进程的绘制指令，将这些指令转换为 GPU 命令缓冲区（Command Buffer），然后提交给 GPU 执行。命令缓冲区机制确保了渲染进程不能直接调用 GPU API，提供了安全隔离。

```
GPU 命令缓冲区工作流程
渲染进程 A ──┐
渲染进程 B ──┼──> 命令缓冲区 ──> GPU 进程 ──> GPU 硬件
渲染进程 C ──┘    (序列化)        (执行)
```

### 2.1.4 网络服务进程（Network Service）

在早期版本中，网络请求由 Browser 进程负责。从 Chrome 73 开始，网络功能被独立为 Network Service 进程。这个变化叫做网络服务进程化（Network Service Process Isolation）。

网络服务进程化的动机：

| 动机 | 说明 |
|------|------|
| 稳定性 | 网络栈崩溃不会影响 Browser 进程 |
| 安全隔离 | 网络代码在沙箱中运行 |
| 可扩展性 | 网络服务可独立重启或迁移 |

网络服务进程负责所有 HTTP/HTTPS 请求、DNS（Domain Name System，域名系统）解析、Cookie 管理、证书验证等网络相关操作。当你在地址栏输入 URL 并回车时，Browser 进程会将请求转发给 Network Service 进程，后者完成 DNS 解析和 HTTP 请求后，将响应数据传回渲染进程。

### 2.1.5 其他进程

**插件进程（Plugin Process）**：为每种类型的插件运行独立进程，如 Pepper 插件（PPAPI，Pepper Plugin API）。由于 Flash 等插件已逐步淘汰，插件进程的使用频率越来越低。

**实用程序进程（Utility Process）**：处理各种低优先级的后台任务，如文件解压、数据解析等。将这些任务放到独立进程可以避免阻塞 Browser 进程。

**存储进程（Storage Service）**：管理 Web Storage（localStorage、sessionStorage）、IndexedDB、Cache API 等浏览器存储。独立的存储进程确保了存储操作不会阻塞网络或 UI。

> Chrome 的进程分工就像一个精密的工厂：Browser 是管理层，Renderer 是生产线，GPU 是美工车间，Network 是物流部，Storage 是仓库。每个部门独立运作，又通过 IPC 紧密协作。

## 2.2 进程间通信（IPC）

### 2.2.1 Mojo IPC 框架

多进程架构的核心挑战是进程间通信。Chrome 早期使用基于命名管道的自定义 IPC 系统，后来逐步迁移到 Mojo 框架。

Mojo 是 Chrome 现代的 IPC（Inter-Process Communication，进程间通信）框架，它提供了多种通信方式：

| 通信方式 | 特点 | 适用场景 |
|---------|------|---------|
| MessagePipe | 双向消息管道，异步 | 通用进程间消息传递 |
| DataPipe | 单向数据流，支持大数据 | 文件传输、媒体流 |
| SharedBuffer | 共享内存，零拷贝 | 大块数据共享 |
| Interface | 类型安全的 RPC 接口 | 结构化的服务调用 |

Mojo 的接口定义语言（IDL，Interface Definition Language）让开发者可以定义类型安全的接口。例如：

```
// Mojo IDL 示例（简化版）
interface NavigationHost {
  // 从 Renderer 请求导航
  RequestNavigation(url.mojom.Url url);
  // 通知导航完成
  DidFinishNavigation(bool success);
};
```

这段 IDL 定义会被代码生成器转换为 C++、JavaScript 等语言的接口代码，各进程通过这些接口进行类型安全的通信。

### 2.2.2 Chromium 中的管道通信

Mojo 的底层实现基于操作系统的 IPC 原语。在不同平台上，Mojo 使用不同的底层机制：

```
Mojo 底层通信机制
┌─────────────┐
│  Mojo API   │  对上层提供统一接口
├─────────────┤
│  Channel    │  序列化/反序列化
├──────┬──────┴──────┬──────────┐
│ Linux│   macOS     │ Windows  │
│ Unix │  Mach       │ Named    │
│ Socket│ Port       │ Pipe     │
└──────┴─────────────┴──────────┘
```

无论底层使用什么机制，Mojo 对上层提供统一的 API。这意味着 Chrome 的业务代码不需要关心平台差异，只需使用 Mojo 接口即可。

### 2.2.3 共享内存与消息传递

对于大数据传递，Mojo 提供了共享内存（Shared Memory）机制。共享内存允许多个进程访问同一块物理内存，避免了数据拷贝的开销。

共享内存的典型使用场景是 GPU 纹理传递。渲染进程将绘制结果写入共享内存，GPU 进程从同一块内存读取数据并生成纹理，整个过程不需要拷贝数据。

```
共享内存工作流程
进程 A                     进程 B
  │                          │
  │  写入数据到共享内存         │
  │────────────────────────►│
  │  (Mojo 通知)              │
  │                          │  从共享内存读取数据
  │                          │
  ▼                          ▼
┌─────────────────────────────┐
│       共享内存区域            │
│  (物理内存，两个进程都可访问)   │
└─────────────────────────────┘
```

> IPC 的性能不仅仅是消息传递的速度，更是减少不必要拷贝的艺术。Mojo 的共享内存机制让大数据传递的成本趋近于零。

## 2.3 站点隔离（Site Isolation）

### 2.3.1 站点隔离的动机与安全收益

站点隔离（Site Isolation）是 Chrome 架构层面最重要的安全特性之一。它的核心思想是：不同站点的页面必须运行在不同的渲染进程中。

为什么需要站点隔离？2018 年发现的 Spectre 和 Meltdown 漏洞证明了：即使有同源策略的保护，共享同一进程的页面仍然可以通过 CPU 侧信道攻击读取彼此的数据。

站点隔离前的架构问题：

```
站点隔离前（同一进程内可能有多个站点）
┌──────────────────────────────┐
│       Renderer 进程           │
│  ┌────────────────────────┐  │
│  │  页面 A（example.com）  │  │
│  │  ┌──────────────────┐  │  │
│  │  │ iframe B（evil.com）│  │
│  │  └──────────────────┘  │  │
│  └────────────────────────┘  │
│  两个站点共享同一进程内存空间    │
│  Spectre 可跨站点读取数据     │
└──────────────────────────────┘
```

站点隔离后的架构：

```
站点隔离后（每个站点独立进程）
┌──────────────────────┐  ┌──────────────────────┐
│   Renderer 进程 A     │  │   Renderer 进程 B     │
│  页面（example.com）   │  │  iframe（evil.com）   │
│  独立内存空间          │  │  独立内存空间          │
│  独立沙箱             │  │  独立沙箱             │
└──────────────────────┘  └──────────────────────┘
        │                           │
        └──── IPC 通信（受控）────────┘
```

站点隔离带来的安全收益：

| 安全收益 | 说明 |
|---------|------|
| 内存隔离 | 不同站点的数据在物理上隔离 |
| Spectre 防御 | 侧信道攻击无法跨进程 |
| 沙箱增强 | 每个站点独立的沙箱限制 |
| 权限隔离 | 一个站点的权限不影响其他站点 |

### 2.3.2 跨站点 iframe 的进程分配

站点隔离引入了一个复杂的问题：一个页面中的跨站点 iframe 需要分配到不同的渲染进程。

例如，你在 example.com 的页面中嵌入了来自 youtube.com 的 iframe，Chrome 会为 example.com 分配一个渲染进程，为 youtube.com 分配另一个渲染进程。

```
跨站点 iframe 的进程分配
浏览器窗口
┌─────────────────────────────────┐
│  example.com 的内容              │
│  ┌───────────────────────────┐  │
│  │  youtube.com 的 iframe     │  │
│  │  (独立渲染进程)             │  │
│  └───────────────────────────┘  │
│  (主页面渲染进程)                 │
└─────────────────────────────────┘

进程视图
┌──────────────┐  ┌──────────────┐
│ Renderer 进程 │  │ Renderer 进程 │
│ example.com   │  │ youtube.com   │
│ (主框架)      │  │ (iframe)     │
└──────────────┘  └──────────────┘
     │  IPC 通信        │
     └──────────────────┘
```

跨进程的 iframe 需要处理很多复杂的情况：事件传播需要跨进程、布局计算需要协调主框架和 iframe 的尺寸、滚动需要同步。Chrome 通过一系列代理对象和 IPC 消息来解决这些问题。

> 站点隔离是 Chrome 安全架构的基石。它不是在代码层面修补漏洞，而是在进程层面隔离风险。一个进程被攻破，不代表所有站点都被攻破。

### 2.3.3 COOP/COEP 与进程隔离的配合

COOP（Cross-Origin Opener Policy，跨源 opener 策略）和 COEP（Cross-Origin Embedder Policy，跨源嵌入策略）是两个 HTTP 头，它们允许页面选择进入更强的隔离级别。

COOP 的作用是确保一个页面不会被其他源的页面通过 window.open 或 target="_blank" 访问到。设置 COOP 后，通过 window.open 打开的页面会运行在独立的进程中。

COEP 的作用是确保页面不加载未经授权的跨源资源。配合 COOP，可以让页面进入「跨源隔离」（Cross-Origin Isolation）状态，从而获得使用 SharedArrayBuffer 等高精度计时器的权限。

关键 HTTP 头配置：

```
# COOP 配置
Cross-Origin-Opener-Policy: same-origin

# COEP 配置
Cross-Origin-Embedder-Policy: require-corp

# 达到跨源隔离状态后可使用
# SharedArrayBuffer、高性能计时器等
```

## 2.4 进程模型策略

Chrome 支持多种进程模型策略，默认使用 process-per-site-instance。

| 策略 | 说明 | 适用场景 |
|------|------|---------|
| process-per-site-instance | 每个站点实例一个进程（默认） | 普通用户 |
| process-per-site | 每个站点一个进程 | 低内存设备 |
| single-process | 所有页面共享一个进程 | 调试/测试 |

process-per-site-instance 的含义是：每个标签页中的每个站点实例都运行在独立的渲染进程中。如果你打开了两个标签页访问同一个网站，它们会各自有独立的渲染进程。这种策略提供了最好的隔离性，但内存开销最大。

在内存受限的设备上（如低端 Android 手机），Chrome 可能会自动切换到 process-per-site 策略，同一站点的所有实例共享一个进程，以减少内存使用。

## 2.5 进程生命周期管理

### 2.5.1 进程的创建与销毁

渲染进程的创建时机是在导航开始时。当用户在地址栏输入 URL 或点击链接时，Browser 进程会检查目标 URL 的站点，然后决定是否创建新的渲染进程或复用现有的。

渲染进程创建流程：

```
导航 → Browser 判断站点 → 是否有同站点可用进程？
                              │
                    ┌─── 是 ──┤── 否 ───┐
                    │                    │
              复用现有进程            创建新进程
                    │                    │
                    └──── 导航到目标 URL ──┘
                              │
                        渲染进程加载页面
```

进程销毁的时机包括：用户关闭标签页、导航到不同站点的页面、以及系统内存压力下的回收。

### 2.5.2 内存压力下的进程回收

Chrome 有一个「标签页丢弃」（Tab Discarding）机制。当系统内存不足时，Chrome 会自动丢弃（Discard）一些不活跃的标签页，释放它们占用的渲染进程内存。

被丢弃的标签页在标签栏仍然可见，但当用户切换到它时，Chrome 会重新创建渲染进程并重新加载页面。

丢弃优先级从低到高：

| 优先级 | 标签页类型 | 被丢弃概率 |
|--------|----------|-----------|
| 1 | 后台标签页（有未保存的表单） | 低 |
| 2 | 后台标签页（最近活跃过） | 中 |
| 3 | 后台标签页（长时间未活跃） | 高 |
| 4 | 被挂起的标签页 | 最高 |

### 2.5.3 渲染进程的挂起与恢复

Chrome 还有一个「渲染进程挂起」（Renderer Suspension）机制。对于长时间不活跃的后台标签页，Chrome 会降低其执行频率，甚至完全挂起 JavaScript 执行。

挂起机制的策略：

| 状态 | JavaScript 执行 | 定时器 | 网络请求 |
|------|----------------|--------|---------|
| 活跃（前台） | 正常 | 正常 | 正常 |
| 后台（短期） | 正常 | 限频（最低 1 次/秒） | 正常 |
| 后台（长期） | 挂起 | 暂停 | 暂停 |
| 被丢弃 | 进程已销毁 | N/A | N/A |

这种策略可以显著减少后台标签页的资源消耗。对于需要持续运行的任务（如音乐播放、实时通信），页面可以通过 Page Visibility API 和 Wake Lock API 来避免被挂起。

> 进程管理就像城市交通调度：高峰期要多开公交线路（创建进程），空闲期要减少班次（挂起进程），拥堵时要砍掉一些线路（丢弃标签页）。目标是在有限的资源下，让用户体验最大化。

## 本章核心知识总结

Chrome 的多进程架构是整个浏览器工作的基础。本章我们拆解了 7 种进程的职责、Mojo IPC 通信框架、站点隔离的安全模型、进程模型策略和生命周期管理。

核心架构对比总结：

| 架构维度 | 传统单进程 | Chrome 多进程 |
|---------|----------|-------------|
| 进程数量 | 1 | N（Browser + N*Renderer + GPU + Network + ...） |
| 标签页隔离 | 无 | 每个站点实例独立进程 |
| 崩溃影响 | 全局崩溃 | 仅影响单个标签页 |
| 安全隔离 | 无内存隔离 | 进程级内存隔离 + 沙箱 |
| IPC 机制 | 不需要 | Mojo（MessagePipe + DataPipe + SharedBuffer） |
| 内存开销 | 低 | 高（多进程基础开销） |
| 进程管理 | 不需要 | 创建/销毁/挂起/丢弃 |
