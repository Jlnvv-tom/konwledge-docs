# 第12章 HTTP/1.1、HTTP/2 与 HTTP/3

> HTTP/1.1 的队头阻塞让浏览器不得不开 6 个连接，HTTP/2 的多路复用解决了这个问题但又引入了 TCP 层的队头阻塞，HTTP/3 干脆把传输层从 TCP 换成了 QUIC。

我是怕浪猫，上期讲了 DNS 和 TCP 基础，今天进入第 12 章：HTTP 协议的三代演进。这一章会拆解 HTTP/1.1 的性能瓶颈、HTTP/2 的多路复用与 Server Push、以及 HTTP/3 基于 QUIC 的创新。

## 12.1 HTTP/1.1 的性能瓶颈

### 12.1.1 队头阻塞（Head-of-Line Blocking）

HTTP/1.1 的核心问题是队头阻塞（HOL Blocking，Head-of-Line Blocking）。在 HTTP/1.1 中，一个 TCP 连接上同时只能处理一个请求。前一个请求的响应未完成时，后续请求必须等待。

```
HTTP/1.1 队头阻塞

连接1：  请求A ──────── 响应A ──────── 请求B ──────── 响应B
                                    ↑ B 必须等 A 完成

浏览器的解决方案：开多个连接（最多6个）
连接1：  请求A ──── 响应A
连接2：  请求B ──── 响应B
连接3：  请求C ──── 响应C
连接4：  请求D ──── 响应D
连接5：  请求E ──── 响应E
连接6：  请求F ──── 响应F

如果超过 6 个资源，第 7 个必须等前面的连接释放
```

### 12.1.2 HTTP/1.1 的优化手段

在 HTTP/1.1 下，开发者发明了各种绕过限制的优化手段。

| 优化手段 | 原理 | 效果 | 副作用 |
|---------|------|------|--------|
| 域名分片 | 使用多个子域名 | 突破 6 连接限制 | 增加 DNS + 连接开销 |
| 雪碧图 | 合并多个图片 | 减少请求数 | 难以维护 |
| 内联资源 | CSS/JS 内联到 HTML | 减少请求数 | 无法缓存 |
| Data URI | 图片转 Base64 | 减少请求数 | 增大 HTML 体积 |
| 合并文件 | 合并 JS/CSS | 减少请求数 | 缓存粒度粗 |

> 域名分片是 HTTP/1.1 时代最常用的优化。把图片放在 img1.example.com 到 img6.example.com，每个子域名各 6 个连接，总共 36 个并发连接。但每个子域名都需要额外的 DNS 解析和 TLS 握手，得不偿失。HTTP/2 时代这些 hack 都可以扔掉了。

### 12.1.3 Keep-Alive 连接复用

HTTP/1.1 默认开启 Keep-Alive，允许在同一个 TCP 连接上发送多个请求。但请求仍然是串行的，前一个响应完成后才能发送下一个。

```http
# HTTP/1.1 Keep-Alive
GET /index.html HTTP/1.1
Host: example.com
Connection: keep-alive

# 响应
HTTP/1.1 200 OK
Content-Length: 1024
Connection: keep-alive
Keep-Alive: timeout=60, max=100

# 在同一连接上发送下一个请求
GET /style.css HTTP/1.1
Host: example.com
```

| 特性 | HTTP/1.0 | HTTP/1.1 |
|------|---------|---------|
| 连接复用 | 默认关闭 | 默认开启（Keep-Alive） |
| 请求方式 | 串行 | 串行（但可复用连接） |
| Host 头 | 可选 | 必需（支持虚拟主机） |
| 缓存 | 基础 | 增强（ETag、Cache-Control） |
| 断点续传 | 不支持 | 支持（Range 请求） |

## 12.2 HTTP/2 的多路复用

### 12.2.1 二进制分帧

HTTP/2 将 HTTP 消息拆分为二进制帧（Frame），在单个 TCP 连接上多路复用。每个请求/响应被分配一个流 ID（Stream ID），帧可以乱序发送，接收端按流 ID 重组。

```
HTTP/2 多路复用

单个 TCP 连接上的 3 个并发请求/响应：

流1（请求A）：  DATA(1) ── DATA(1) ── DATA(1,END)
流3（请求B）：  DATA(3) ── DATA(3) ── DATA(3,END)
流5（请求C）：  DATA(5) ── DATA(5) ── DATA(5,END)

实际在 TCP 上发送的帧序列（可交错）：
  DATA(1) | DATA(3) | DATA(5) | DATA(1) | DATA(3) | DATA(5) | ...

接收端按流 ID 重组：
  流1 → 完整响应A
  流3 → 完整响应B
  流5 → 完整响应C
```

### 12.2.2 HTTP/2 帧类型

HTTP/2 定义了多种帧类型，每种帧有不同的功能。

| 帧类型 | 说明 | 用途 |
|--------|------|------|
| DATA | 数据帧 | 传输请求/响应体 |
| HEADERS | 头部帧 | 传输请求/响应头 |
| PRIORITY | 优先级帧 | 设置流的优先级 |
| RST_STREAM | 重置帧 | 取消流 |
| SETTINGS | 设置帧 | 连接参数协商 |
| PUSH_PROMISE | 推送承诺帧 | 服务器推送通知 |
| PING | 心跳帧 | 连接保活 |
| GOAWAY | 关闭帧 | 优雅关闭连接 |
| WINDOW_UPDATE | 窗口更新帧 | 流量控制 |
| CONTINUATION | 续帧 | 继续头部块 |

### 12.2.3 HPACK 头部压缩

HTTP/2 使用 HPACK 算法压缩头部。HPACK 通过静态表、动态表和哈夫曼编码减少头部大小。

```
HTTP/1.1 头部（重复传输）：
  GET / HTTP/1.1
  Host: example.com        ← 每次请求都发送
  User-Agent: Mozilla/5.0  ← 每次请求都发送
  Accept: text/html        ← 每次请求都发送
  Cookie: session=abc123   ← 每次请求都发送

HTTP/2 HPACK 压缩：
  首次请求：发送完整头部 → 存入动态表
  后续请求：只发送变化的头部 → 引用动态表
  
  压缩率可达 80-90%
```

| HPACK 组件 | 说明 | 效果 |
|-----------|------|------|
| 静态表 | 61 个常见头部字段预定义 | 常用头部用索引代替 |
| 动态表 | 连接内共享的头部历史 | 重复头部只发一次 |
| 哈夫曼编码 | 字符串压缩 | 减少字符串体积 |

HPACK 的动态表是连接级别的，所有流共享一个动态表。这意味着第一个请求发送的 Cookie 头部可以被后续请求引用，不需要重复发送。动态表的大小由 SETTINGS 帧协商，默认 4096 字节。

### 12.2.4 流优先级

HTTP/2 允许客户端为每个流设置优先级，告诉服务器哪些资源更重要，应该优先分配带宽。

在 HTTP/2 的早期版本中，优先级通过 PRIORITY 帧设置，采用树形依赖结构。但在实际使用中，这个树形结构过于复杂，服务器实现困难。HTTP/2 后来引入了简化的优先级方案： urgency（紧急程度）和 incremental（是否可增量）。

```javascript
// 使用 fetch 设置优先级（HTTP/2）
fetch('/critical.css', {
  priority: 'high'  // 高优先级
});

fetch('/analytics.js', {
  priority: 'low'   // 低优先级
});
```

| 优先级 | 适用资源 | 说明 |
|--------|---------|------|
| highest | 关键 CSS | 首屏渲染必需 |
| high | 关键 JS | 交互功能必需 |
| medium | 图片 | 视觉填充 |
| low | 分析脚本 | 后台上报 |
| lowest | 预加载资源 | 未来可能使用 |

### 12.2.4 Server Push

HTTP/2 的 Server Push 允许服务器在客户端请求 HTML 时，主动推送 HTML 中引用的 CSS、JS 等资源。

```
Server Push 流程

客户端请求 GET /index.html
  │
  ▼
服务器响应 index.html
  同时发送 PUSH_PROMISE（承诺推送 /style.css）
  │
  ▼
客户端收到 PUSH_PROMISE
  ├─ 如果已有缓存 → 发送 RST_STREAM 拒绝
  └─ 如果没有缓存 → 接受推送
  │
  ▼
服务器推送 /style.css 的内容
```

Server Push 的实际效果并不理想。服务器很难准确判断客户端是否已经缓存了资源，导致推送了不需要的内容，浪费带宽。Chrome 在 105 版本中移除了对 HTTP/2 Server Push 的支持。

> Server Push 是 HTTP/2 中一个听起来美好但实际效果不佳的特性。服务器无法知道客户端的缓存状态，推送了已缓存的资源反而浪费带宽。Chrome 已经移除了这个功能，推荐使用 `<link rel="preload">` 替代。

### 12.2.6 HTTP/2 的实际性能表现

HTTP/2 在实际使用中的性能提升主要来自多路复用和头部压缩。对于一个加载 50 个资源的页面，HTTP/2 的优势非常明显。

| 场景 | HTTP/1.1 | HTTP/2 | 提升 |
|------|---------|--------|------|
| 50 个小资源 | 6 连接串行 | 1 连接并发 | 3-5x |
| 大量重复头部 | 每次完整发送 | HPACK 压缩 | 80% 带宽 |
| 单个大文件 | 单连接 | 单连接 | 无提升 |
| API 请求 | 6 连接限制 | 无限制 | 消除排队 |

但 HTTP/2 并非在所有场景下都比 HTTP/1.1 快。当只有一个大文件下载时，HTTP/2 和 HTTP/1.1 性能相当，因为多路复用和头部压缩的优势在这种场景下不存在。

## 12.3 HTTP/3 与 QUIC

### 12.3.1 TCP 层的队头阻塞

HTTP/2 解决了 HTTP 层的队头阻塞，但 TCP 层仍有队头阻塞。TCP 保证数据的有序传输，如果一个 TCP 包丢失，后续包必须等待重传。

```
TCP 层队头阻塞

HTTP/2 多路复用，3 个流共享一个 TCP 连接：

发送序列：  包1(流1) | 包2(流3) | 包3(流5) | 包4(流1) | ...

如果包2丢失：
  包1 → 接收 ✓
  包2 → 丢失 ✗ → 等待重传
  包3 → 到达但被 TCP 缓存（因为必须按序交付）
  包4 → 同上

结果：流5的数据被流3的丢包阻塞
      即使流5的数据已经到达，也不能交付给应用
```

### 12.3.2 QUIC 协议

HTTP/3 将传输层从 TCP 换成了 QUIC（Quick UDP Internet Connections，快速 UDP 互联网连接）。QUIC 基于 UDP，在用户空间实现了可靠传输、拥塞控制和加密。

```
HTTP/3 协议栈对比

HTTP/1.1 和 HTTP/2：
  HTTP → TLS → TCP → IP

HTTP/3：
  HTTP → QUIC → UDP → IP
  
QUIC 内部集成了 TLS 1.3
  不需要额外的 TLS 层
```

| 特性 | TCP + TLS | QUIC |
|------|-----------|------|
| 传输层 | TCP | UDP |
| 加密 | TLS（独立层） | 集成 TLS 1.3 |
| 队头阻塞 | 有（流间影响） | 无（流独立） |
| 连接迁移 | 不支持 | 支持（IP 变化不断连） |
| 连接建立 | TCP 3次握手 + TLS 握手 | 1-RTT（或 0-RTT） |
| 拥塞控制 | 内核空间 | 用户空间（灵活） |

### 12.3.3 QUIC 的流独立性

QUIC 的每个流有独立的确认和重传机制。一个流的丢包只影响该流，不影响其他流。

```
QUIC 流独立性

流1：  数据1 ──── 数据2 ──── 数据3 ────
流3：  数据1 ──── [丢失] ──── 数据3 ────
流5：  数据1 ──── 数据2 ──── 数据3 ────

流3的数据2丢失：
  流1 → 正常交付 ✓
  流3 → 数据2等待重传，数据3缓存
  流5 → 正常交付 ✓

流5 不受流3丢包影响！
```

### 12.3.4 连接迁移

QUIC 使用 Connection ID（连接 ID）标识连接，而不是像 TCP 那样依赖 IP 地址和端口。当设备切换网络（如从 WiFi 切换到 4G）时，IP 地址变化但 QUIC 连接不断。

```
连接迁移示例

设备从 WiFi 切换到 4G：
  WiFi: IP=192.168.1.100, Port=12345
  4G:   IP=10.0.0.50, Port=54321

TCP：
  IP 变化 → TCP 连接断开 → 必须重新建立连接
  （DNS + TCP 握手 + TLS 握手）

QUIC：
  IP 变化 → Connection ID 不变 → 连接保持
  继续发送数据，无感知切换
```

### 12.3.5 QUIC 的拥塞控制

QUIC 在用户空间实现拥塞控制，可以比内核空间的 TCP 更快地迭代算法。QUIC 支持 CUBIC、BBR、BBRv2 等多种拥塞控制算法。

QUIC 的拥塞控制还有一个优势：更精确的 RTT 测量。TCP 的 RTT 测量受重传歧义影响（无法确认收到的 ACK 是对原始包还是重传包的确认）。QUIC 在包级别使用唯一单调递增的包号，重传的包使用新包号，彻底消除了重传歧义。

| 拥塞控制特性 | TCP | QUIC |
|------------|-----|------|
| 实现位置 | 内核空间 | 用户空间 |
| 算法迭代 | 需要内核更新 | 随浏览器更新 |
| RTT 测量 | 有重传歧义 | 精确 |
| 包号 | 重传复用 | 单调递增 |

> 连接迁移是 QUIC 的杀手锏。在移动场景下，用户从 WiFi 切换到蜂窝网络时，TCP 连接会断开，页面加载中断。QUIC 的连接迁移让这个过程无感知，用户甚至不会感觉到网络切换。

## 12.4 三个版本对比

### 12.4.1 核心特性对比

| 特性 | HTTP/1.1 | HTTP/2 | HTTP/3 |
|------|---------|--------|--------|
| 传输层 | TCP | TCP | QUIC（UDP） |
| 多路复用 | 否 | 是 | 是 |
| 队头阻塞 | HTTP 层 | TCP 层 | 无 |
| 头部压缩 | 否 | HPACK | QPACK |
| 加密 | 可选 | 可选（实践中必须） | 强制（TLS 1.3 集成） |
| Server Push | 否 | 是（已废弃） | 否 |
| 连接建立 RTT | 1-RTT（TCP）+ 1-RTT（TLS） | 同 HTTP/1.1 | 1-RTT（或 0-RTT） |
| 连接迁移 | 不支持 | 不支持 | 支持 |

### 12.4.2 连接建立时间对比

```
连接建立时间对比

HTTP/1.1（HTTPS）：
  DNS(1RTT) + TCP(1RTT) + TLS(1-2RTT) + 请求(1RTT)
  = 4-5 RTT

HTTP/2（HTTPS）：
  DNS(1RTT) + TCP(1RTT) + TLS(1-2RTT) + 请求(1RTT)
  = 4-5 RTT（与 HTTP/1.1 相同）
  但后续请求可多路复用

HTTP/3（首次连接）：
  DNS(1RTT) + QUIC握手(1RTT，含TLS) + 请求(0RTT，握手同时发数据)
  = 2 RTT

HTTP/3（会话恢复）：
  DNS(1RTT) + QUIC(0RTT，数据在握手前发送)
  = 1 RTT
```

## 12.5 QPACK 头部压缩

### 12.5.1 QPACK 与 HPACK 的差异

HTTP/3 使用 QPACK 替代 HTTP/2 的 HPACK。QPACK 针对 QUIC 的流独立性做了适配。

| 特性 | HPACK | QPACK |
|------|-------|-------|
| 静态表 | 61 项 | 99 项 |
| 动态表 | 连接级共享 | 连接级共享 |
| 编码 | 同步 | 异步（带确认） |
| 流阻塞 | 可能 | 避免动态表引用 |

QPACK 的核心设计是避免头部压缩引入的流间阻塞。QPACK 对动态表的引用是异步的，如果一个引用了动态表的请求被阻塞，不会影响其他请求。

QPACK 的工作方式是：当请求需要引用动态表中的条目时，它发送一个引用索引。如果动态表中的条目尚未被确认（可能是新加入的），请求标记为「可能需要阻塞」。接收端收到后，如果引用有效，正常处理；如果引用无效（动态表条目已被淘汰），发送一个拒绝信号，发送方回退到字面值编码。

### 12.5.2 QPACK 的插入计数

QPACK 使用 Insert Count（插入计数）来同步发送方和接收方的动态表状态。发送方每次向动态表插入新条目时，计数加一。接收端通过 ACK 帧确认它已收到的动态表条目数。

这个机制确保了即使某些包丢失或乱序，动态表的状态也能正确同步。如果发送方收到确认后发现某些动态表条目未被接收方收到，它可以重发这些条目或回退到字面值编码。

> QPACK 比 HPACK 复杂得多，但这种复杂度是值得的。HTTP/2 的 HPACK 可能导致流间阻塞（一个流的头部引用了动态表，动态表更新被另一个流阻塞），QPACK 通过异步确认机制彻底解决了这个问题。

## 12.6 浏览器对 HTTP/3 的支持

### 12.6.1 HTTP/3 的发现机制

浏览器如何知道服务器支持 HTTP/3？有两种机制：

```
HTTP/3 发现机制

1. Alt-Svc 头（HTTP/2 响应中）
   HTTP/2 200 OK
   Alt-Svc: h3=":443"; ma=86400
   
   浏览器收到后，下次请求尝试用 HTTP/3

2. DNS SVCB/HTTPS 记录
   example.com. IN HTTPS 1 . alpn=h3
   
   浏览器从 DNS 记录中发现 HTTP/3 支持
   可以在首次请求就用 HTTP/3
```

| 发现方式 | 说明 | 首次可用？ |
|---------|------|-----------|
| Alt-Svc | 通过 HTTP/2 响应头通知 | 否（先用 HTTP/2） |
| DNS SVCB | 通过 DNS 记录通知 | 是（首次即可用） |

> HTTP/3 的发现需要一次「升级」过程。首次访问通常走 HTTP/2，服务器通过 Alt-Svc 头告知支持 HTTP/3，浏览器下次才用 HTTP/3。DNS SVCB 记录可以让首次访问就走 HTTP/3，但需要 DNS 基础设施支持。

### 12.6.2 HTTP/3 的部署挑战

HTTP/3 的部署比 HTTP/2 复杂得多。HTTP/2 只需要服务器软件升级，底层 TCP 不变。HTTP/3 需要 QUIC 支持，而 QUIC 基于 UDP，许多网络设备对 UDP 流量做了限速或阻断。

| 挑战 | 说明 | 解决方案 |
|------|------|----------|
| UDP 限速 | 部分 ISP/企业网络限制 UDP | 连接失败回退 HTTP/2 |
| 中间盒兼容 | 某些防火墙阻止 QUIC | 检测并回退 |
| 服务器支持 | 需要 QUIC 实现 | Nginx/Caddy 已支持 |
| 调试困难 | QUIC 加密更难抓包 | 需专用工具 |

Chrome 实现了智能回退机制：如果 QUIC 连接失败，自动回退到 HTTP/2 over TCP，不影响用户体验。这使得 HTTP/3 的部署可以渐进进行，不会因为兼容性问题导致页面无法访问。

| 知识模块 | 核心内容 | 性能影响 |
|---------|---------|---------|
