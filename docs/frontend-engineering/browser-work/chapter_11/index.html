第11章 DNS 与网络协议基础

输入网址到页面开始加载，第一步是 DNS 解析。这个过程通常只需几十毫秒，但背后涉及本地缓存、系统缓存、路由器缓存、递归查询、根域名服务器等多个层级。

我是怕浪猫，从这章开始我们进入网络栈。第 11 章讲 DNS（Domain Name System，域名系统）解析过程、TCP（Transmission Control Protocol，传输控制协议）连接建立与拥塞控制、以及浏览器如何管理网络连接池。

11.1 DNS 解析的全过程​

11.1.1 DNS 解析的层级​

DNS 解析是将域名转换为 IP 地址的过程。这个过程涉及多个层级的缓存和查询。

DNS 解析完整流程

1. 浏览器 DNS 缓存
   Chrome 维护自己的 DNS 缓存
   命中 → 直接返回 IP
   │
   ▼ 未命中
2. 操作系统 DNS 缓存
   OS 维护系统级 DNS 缓存
   命中 → 直接返回 IP
   │
   ▼ 未命中
3. 本地 hosts 文件
   检查 /etc/hosts（Linux/macOS）
   或 C:\Windows\System32\drivers\etc\hosts（Windows）
   命中 → 直接返回 IP
   │
   ▼ 未命中
4. 本地 DNS 服务器（递归解析器）
   通常是 ISP（Internet Service Provider，互联网服务提供商）的 DNS
   或配置的公共 DNS（如 8.8.8.8、114.114.114.114）
   命中 → 直接返回 IP
   │
   ▼ 未命中
5. 递归查询
   本地 DNS 服务器代替浏览器进行递归查询
   ├─ 查询根域名服务器（Root Server）
   ├─ 查询顶级域名服务器（TLD Server）
   └─ 查询权威域名服务器（Authoritative Server）
   │
   ▼
6. 返回 IP 地址
   逐层缓存，下次直接命中

11.1.2 DNS 记录类型​

DNS 不仅存储域名到 IP 的映射，还存储其他类型的记录。

记录类型全称说明示例
AAddress域名到 IPv4 地址example.com → 93.184.216.34
AAAAIPv6 Address域名到 IPv6 地址example.com → 2606:2800:220:1:...
CNAMECanonical Name域名别名www.example.com → example.com
MXMail Exchange邮件服务器example.com → mail.example.com
NSName Server域名服务器example.com → ns1.example.com
TXTText任意文本SPF、DKIM 验证
SOAStart of Authority域权威信息主服务器、管理员邮箱等
SRVService服务记录指定服务的端口和主机

11.1.3 DNS 缓存与 TTL​

DNS 记录有一个 TTL（Time To Live，生存时间）字段，控制缓存的有效期。TTL 越短，DNS 变更生效越快，但查询频率越高；TTL 越长，缓存命中率越高，但变更生效越慢。

DNS 缓存 TTL 示例

example.com 的 A 记录：
  IP: 93.184.216.34
  TTL: 3600（1小时）

缓存行为：
  第一次查询 → 递归查询 → 获得 IP + TTL=3600
  缓存 1 小时
  1 小时内的查询 → 直接返回缓存
  1 小时后 → 缓存过期 → 重新查询
TTL 值适用场景优缺点
60s（1分钟）频繁变更 IP变更快，但查询多
3600s（1小时）一般场景平衡
86400s（1天）稳定 IP查询少，但变更慢

Chrome 的 DNS 缓存有自己的过期策略，不完全依赖 DNS 记录的 TTL。Chrome 会对即将过期的记录提前刷新，避免在关键请求时等待 DNS 解析。

11.1.4 DNS 预解析​

Chrome 支持 DNS 预解析（DNS Prefetching），提前解析可能访问的域名，减少后续请求的延迟。

<!-- 预解析单个域名 -->
<link rel="dns-prefetch" href="//api.example.com">

<!-- 预连接（DNS + TCP + TLS） -->
<link rel="preconnect" href="//api.example.com">
优化方式做了什么开销效果
dns-prefetch只做 DNS 解析极小节省 DNS 时间
preconnectDNS + TCP + TLS小节省全部连接时间
preloadDNS + 连接 + 请求中提前获取资源

Chrome 还会自动学习用户的浏览模式，对可能访问的域名做隐式预解析。比如页面中的链接、图片 src 等，Chrome 可能在用户点击前就预解析 DNS。

11.2 TCP 连接建立​

11.2.1 三次握手​

TCP（Transmission Control Protocol，传输控制协议）使用三次握手（Three-Way Handshake）建立连接。

TCP 三次握手

客户端                                    服务器
  │                                         │
  │  SYN（seq=x）                           │
  │ ──────────────────────────────────────► │
  │           SYN-RCVD 状态                  │
  │                                         │
  │  SYN+ACK（seq=y, ack=x+1）              │
  │ ◄────────────────────────────────────── │
  │  ESTABLISHED 状态                       │
  │                                         │
  │  ACK（ack=y+1）                         │
  │ ──────────────────────────────────────► │
  │           ESTABLISHED 状态              │
  │                                         │
  │  可以开始发送数据                        │

三次握手的意义：

步骤作用说明
SYN客户端发起连接告诉服务器我想连接
SYN+ACK服务器确认并回应告诉客户端我准备好了
ACK客户端确认双方都知道连接已建立

11.2.2 TCP 拥塞控制​

TCP 通过拥塞控制算法避免网络拥塞。Chrome 默认使用 BBR（Bottleneck Bandwidth and Round-trip propagation time）或 CUBIC 拥塞控制算法。

TCP 拥塞控制四个阶段

1. 慢启动（Slow Start）
   初始拥塞窗口（cwnd）= 10 MSS（最大报文段长度）
   每收到一个 ACK，cwnd 加 1
   cwnd 呈指数增长：10 → 20 → 40 → 80 → ...

2. 拥塞避免（Congestion Avoidance）
   当 cwnd 达到慢启动阈值（ssthresh）时
   改为线性增长：每个 RTT（Round-Trip Time，往返时延）cwnd 加 1

3. 快速重传（Fast Retransmit）
   收到 3 个重复 ACK → 立即重传丢失的包
   不等待超时

4. 快速恢复（Fast Recovery）
   ssthresh = cwnd / 2
   cwnd = ssthresh
   继续拥塞避免
拥塞控制算法特点Chrome 使用
CUBIC基于丢包的拥塞控制旧版本默认
BBR基于带宽和延迟的拥塞控制新版本默认
New Reno经典算法不会使用

BBR 算法的优势在于不依赖丢包来判断拥塞，而是通过测量带宽和 RTT 来调整发送速率。在高延迟网络中，BBR 比 CUBIC 性能更好。

11.2.3 TCP 优化技术​

现代 TCP 实现包含多种优化技术，减少连接建立和数据传输的延迟。

优化技术全称说明效果
TFOTCP Fast Open首次握手时携带数据节省 1 RTT
SACKSelective Acknowledgment选择性确认减少重传
Window Scaling—窗口缩放支持大窗口
Timestamps—时间戳更精确 RTT
ECNExplicit Congestion Notification显式拥塞通知提前感知拥塞

TCP Fast Open（TFO）是 Chrome 支持的一个优化。在首次连接时，客户端获取一个 TFO Cookie。后续连接时，客户端在 SYN 包中携带 TFO Cookie 和请求数据，服务器验证 Cookie 后立即处理数据，不需要等待三次握手完成。

TCP 的各种优化技术本质上都在做一件事：减少等待时间。从三次握手到 TFO，从 CUBIC 到 BBR，每一次优化都是在寻找「等」的环节并想办法消除它。

11.3.2 连接池管理​

Chrome 维护一个网络连接池，复用已建立的 TCP/TLS 连接，避免每次请求都重新建立连接。

连接池工作流程

请求 https://api.example.com/data
  │
  ▼
检查连接池
  ├─ 有空闲的 api.example.com:443 连接？
  │   ├─ 有 → 复用连接
  │   └─ 没有 → 新建连接
  │
  ▼
发送请求
  │
  ▼
请求完成
  ├─ 连接保持打开（keep-alive）
  └─ 放回连接池
  │
  ▼
下次请求同一域名
  └─ 从连接池取出连接复用

连接池参数：
  - 每个域名最大连接数：6（HTTP/1.1）
  - 连接空闲超时：~60秒
  - 总最大连接数：255
协议每域名最大连接说明
HTTP/1.16浏览器限制
HTTP/21（多路复用）一个连接处理多个请求
HTTP/31（多路复用）同 HTTP/2

HTTP/2 和 HTTP/3 的多路复用让一个 TCP/QUIC 连接可以同时处理多个请求，不需要像 HTTP/1.1 那样维护多个连接。这也是为什么 HTTP/2 在加载多资源页面时比 HTTP/1.1 快得多。

11.3.3 Socket Pool 的实现​

Chrome 的 Socket Pool 基于 Mojo IPC 通信。网络请求不一定在渲染进程中执行，而是在 Network Service（网络服务）中统一管理。Network Service 是一个独立的服务，所有渲染进程的网络请求都通过它处理。

这种集中式网络管理的好处是：连接池可以跨标签页共享，同一个域名的连接可以在不同标签页之间复用。同时，网络逻辑的崩溃不会影响渲染进程，提高了浏览器的稳定性。

特性传统架构Chrome 网络服务架构
网络请求位置渲染进程内独立 Network Service
连接池共享仅标签页内跨标签页共享
崩溃隔离网络崩溃影响渲染独立崩溃不影响渲染
Cookie 管理各进程分别管理集中管理

11.4 TLS 握手过程​

11.4.1 TLS 1.3 握手​

TLS（Transport Layer Security，传输层安全协议）是 HTTPS 的基础。TLS 1.3 是当前最新的版本，它将握手过程从 TLS 1.2 的 2-RTT 减少到 1-RTT。

TLS 1.3 握手过程

客户端                                    服务器
  │                                         │
  │  ClientHello                            │
  │  （含支持的密码套件、密钥共享）            │
  │ ──────────────────────────────────────► │
  │                                         │
  │  ServerHello                            │
  │  （选定密码套件、密钥共享）                │
  │  EncryptedExtensions                    │
  │  Certificate（服务器证书）               │
  │  CertificateVerify                      │
  │  Finished                               │
  │ ◄────────────────────────────────────── │
  │                                         │
  │  Finished                               │
  │ ──────────────────────────────────────► │
  │                                         │
  │  可以开始发送应用数据                     │

总耗时：1-RTT

11.4.2 TLS 1.3 vs TLS 1.2​

特性TLS 1.2TLS 1.3
握手 RTT2-RTT1-RTT
会话恢复1-RTT0-RTT
密码套件数量多少（精简）
前向安全可选强制
不安全算法支持一些全部移除

11.4.3 0-RTT 会话恢复​

TLS 1.3 支持 0-RTT（Zero Round-Trip Time）会话恢复，在恢复之前的 TLS 会话时，不需要额外的握手往返。

0-RTT 会话恢复

首次连接：
  ClientHello → ServerHello → 数据传输
  （1-RTT，服务器返回 PSK（Pre-Shared Key））

再次连接（会话恢复）：
  ClientHello + 0-RTT 数据 → 服务器
  服务器验证 PSK 后立即处理数据
  （0-RTT，数据在握手完成前就发送了）

注意：0-RTT 数据有重放攻击风险
     服务器需要做重放检测

0-RTT 是 TLS 1.3 的重要优化。对于已建立过连接的服务器，Chrome 可以在第一个数据包中就携带请求数据，将连接建立时间减少到 0。但 0-RTT 数据有重放攻击风险，只适合幂等请求（如 GET）。

11.4.4 证书透明度​

Certificate Transparency（CT，证书透明度）是 Chrome 要求所有公开信任的 TLS 证书必须记录到公开的 CT 日志中。这个机制旨在防止证书颁发机构（CA，Certificate Authority）错误签发证书。

Chrome 在建立 TLS 连接时会验证服务器证书是否包含 CT 日志的签名。如果没有，Chrome 会拒绝连接或显示警告。这确保了每个公开证书都可以被独立审计。

11.5 Secure DNS 与 DNS-over-HTTPS​

11.5.1 DNS 的隐私问题​

传统 DNS 查询使用 UDP（User Datagram Protocol，用户数据报协议）明文传输，任何中间人都可以看到你查询了什么域名。这是一个隐私问题。

11.5.2 DNS-over-HTTPS​

DNS-over-HTTPS（DoH）将 DNS 查询封装在 HTTPS 请求中，加密 DNS 查询内容。

传统 DNS vs DoH

传统 DNS：
  浏览器 → UDP 53 → DNS 服务器
  明文传输，中间人可见

DoH：
  浏览器 → HTTPS 443 → DoH 服务器
  加密传输，中间人不可见
DNS 方式传输协议加密端口
传统 DNSUDP/TCP否53
DNS-over-TLS（DoT）TLS是853
DNS-over-HTTPS（DoH）HTTPS是443

Chrome 支持配置 DoH，用户可以选择使用 Cloudflare（1.1.1.1）或 Google（8.8.8.8）等 DoH 服务器。

11.5.3 DNS 安全扩展​

DNSSEC（Domain Name System Security Extensions，DNS 安全扩展）是 DNS 的安全协议，它通过数字签名验证 DNS 响应的真实性，防止 DNS 劫持和缓存投毒。

DNSSEC 的工作原理是：DNS 记录附带数字签名，客户端通过验证签名确认记录来自权威服务器且未被篡改。DNSSEC 不加密 DNS 查询（它不是 DoH 的替代品），但确保查询结果的完整性。

安全机制防护目标加密完整性
传统 DNS无否否
DNSSECDNS 劫持/投毒否是
DoH窃听是是
DoH + DNSSEC全面是是

11.6 浏览器网络请求的生命周期​

11.6.1 请求状态机​

Chrome 的网络请求经过一系列状态转换，从 URL 解析到最终响应。每个状态对应不同的处理逻辑。

请求状态转换

URL 解析
  │  解析 URL，提取协议/域名/端口/路径
  ▼
DNS 解析
  │  域名 → IP 地址
  ▼
连接建立
  │  TCP 握手 + TLS 握手
  ▼
发送请求
  │  请求行 + Headers + Body
  ▼
等待响应
  │  服务器处理请求
  ▼
接收响应
  │  响应 Headers + Body
  ▼
处理重定向
  │  如果 3xx → 回到 URL 解析
  ▼
完成

11.6.2 重定向处理​

当服务器返回 3xx 状态码时，Chrome 需要跟随重定向。重定向涉及 DNS 解析、连接建立等完整流程，可能显著增加页面加载时间。

重定向类型状态码说明缓存？
永久重定向301资源永久移动是
临时重定向302资源临时移动否
临时重定向307保持方法的临时重定向否
永久重定向308保持方法的永久重定向是

每次重定向都增加一个 RTT 的延迟。如果你的页面从 http → https → www.example.com → example.com，那是 3 次重定向。尽量减少重定向链，特别是首屏加载时。

11.7 HTTP/1.1 Keep-Alive 与管线化​

11.7.1 Keep-Alive 的详细工作机制​

HTTP/1.1 的 Keep-Alive 机制允许在同一个 TCP 连接上发送多个请求，避免了每次请求都重新建立 TCP 连接的开销。但 Keep-Alive 并不意味着请求可以并行——请求仍然是串行的。

HTTP/1.1 Keep-Alive 工作流程

TCP 连接建立 (3次握手 + TLS 握手)
  │
  ▼
请求1: GET /index.html → 响应1
  │ (连接保持打开)
  ▼
请求2: GET /style.css → 响应2
  │ (连接保持打开)
  ▼
请求3: GET /script.js → 响应3
  │
  ▼
空闲超时 (60秒无请求)
  │
  ▼
连接关闭

优势:
  节省了请求2和请求3的 TCP/TLS 握手时间
  (约 1-2 RTT per connection)

劣势:
  请求仍然串行 (请求2必须等响应1完成)

11.7.2 HTTP/1.1 管线化（Pipelining）的失败​

HTTP/1.1 规范实际上定义了管线化（Pipelining）——允许在同一个连接上连续发送多个请求，不等响应就发送下一个。但这个特性在实践中几乎从未被使用。

HTTP/1.1 管线化

请求1: GET /index.html ──────── 响应1
请求2: GET /style.css  ────── 响应2
请求3: GET /script.js ────── 响应3

请求连续发送，但响应必须按序返回 (FIFO)

问题: 队头阻塞 (HOL Blocking)
  如果响应1很慢 (大文件)，响应2和3即使已准备好
  也必须等响应1完成才能发送
  → 管线化比 Keep-Alive 串行更差
  → 浏览器默认禁用管线化

管线化失败的原因：响应必须按序返回（HTTP/1.1 的限制）、中间代理可能不支持管线化导致连接失败、管线化请求的幂等性要求限制。Chrome 从未默认启用过 HTTP/1.1 管线化。

11.8 HTTP/2 的 HPACK 头部压缩算法​

11.8.1 HPACK 的三个组件​

HPACK 是 HTTP/2 的头部压缩算法，它通过三个组件协同工作减少头部大小。

HPACK 工作流程

组件1: 静态表 (Static Table)
  预定义了 61 个最常见的 HTTP 头部字段
  ├─ 1: :authority
  ├─ 2: :method GET
  ├─ 3: :method POST
  ├─ 4: :path /
  ├─ 6: accept-encoding
  ├─ 8: accept-language
  └─ ...
  
  发送时只需引用索引号，如:
  "索引 2" → :method GET
  (从 15 字节压缩到 1 字节)

组件2: 动态表 (Dynamic Table)
  连接内共享的头部历史记录
  首次发送完整头部 → 存入动态表
  后续请求引用动态表索引
  
  请求1: cookie: session=abc123... (完整发送)
         → 存入动态表[0]
  请求2: 引用动态表[0] (1 字节)

组件3: 哈夫曼编码 (Huffman Coding)
  对字符串值进行哈夫曼编码
  高频字符用短编码，低频字符用长编码
  ├─ 'e' (高频) → 3 bits
  ├─ 'x' (低频) → 11 bits
  └─ 平均压缩率 30-50%

11.8.2 HPACK 压缩效果实测​

头部字段原始大小HPACK 压缩后压缩率
:method GET12B1B (静态表)92%
:path /7B1B (静态表)86%
user-agent120B45B (动态表+哈夫曼)63%
cookie500B30B (动态表引用)94%
accept-encoding25B1B (静态表)96%

首次请求的压缩率较低（因为动态表还没建立），后续请求的压缩率可达 80-95%。Cookie 是压缩收益最大的字段——同一个域名的请求通常携带相同的 Cookie，存入动态表后只需引用索引。

11.9 HTTP/2 优先级与依赖树​

11.9.1 HTTP/2 的优先级模型​

HTTP/2 早期版本定义了一个基于依赖树的优先级模型。每个流可以依赖另一个流，形成树形结构。服务器根据依赖树分配带宽和资源。

HTTP/2 优先级依赖树

         根
        / | \
      A   B   C
      |   |   |
      D   E   F
     / \
    G   H

优先级规则:
  A、B、C 平分根的带宽
  D 获得 A 的全部带宽
  G、H 平分 D 的带宽
  
权重 (weight 1-256):
  如果 A 和 B 都有权重 128
  → 各获得 50% 带宽
  如果 A=128, B=256
  → A 获得 1/3, B 获得 2/3

这个模型过于复杂，实际服务器实现困难。RFC 9218 引入了简化的优先级方案：urgency (1-7) 和 incremental (bool)。

11.9.2 简化后的优先级方案​

// fetch API 设置优先级
fetch('/critical.css', {
  priority: 'high'    // urgency=1
});

fetch('/image.jpg', {
  priority: 'auto'    // urgency=3 (默认)
});

fetch('/analytics', {
  priority: 'low'     // urgency=6
});
urgency 值语义适用资源
1highest关键 CSS、首屏字体
2high关键 JS、首屏图片
3-4medium普通资源
5-6low分析脚本、预加载
7lowest后台同步

11.10 HTTP/3 的 QPACK 头部压缩​

11.10.1 QPACK 与 HPACK 的关键差异​

QPACK 是 HTTP/3 的头部压缩算法，专为 QUIC 的流独立性设计。HPACK 的动态表引用可能导致流间阻塞（一个流的头部引用了动态表，但动态表的更新在另一个流中被阻塞）。QPACK 通过异步确认机制解决了这个问题。

QPACK 异步确认机制

流1 发送请求:
  引用动态表[3]
  但动态表[3] 是最近插入的，尚未被确认
  → 标记为 "可能需要阻塞"
  → 如果接收端已有动态表[3]，正常处理
  → 如果没有，接收端发送拒绝信号
  → 发送方回退到字面值编码

流3 同时发送请求:
  不引用动态表
  → 独立处理，不受流1的影响
  → QUIC 的流独立性得以保持

11.10.2 0-RTT 早期数据的安全风险​

0-RTT 虽然减少了延迟，但引入了重放攻击（Replay Attack）的风险。攻击者可以截获 0-RTT 数据包，重复发送给服务器。

0-RTT 重放攻击

1. 客户端发送 0-RTT 请求
   POST /transfer
   { to: "attacker", amount: 1000 }
   
2. 攻击者截获请求包
   
3. 攻击者重放请求包给服务器
   服务器收到重复的 POST /transfer
   → 如果服务器不做重放检测
   → 重复执行转账!

0-RTT 的安全限制：只允许幂等请求（GET、HEAD）、服务器必须实现重放检测（如使用 nonce 或时间戳）、0-RTT 数据有有效期限制（通常几分钟）、PSK（Pre-Shared Key）有过期时间。

11.10.3 HTTP/3 连接迁移​

HTTP/3 基于 QUIC，继承了 QUIC 的连接迁移能力。当设备切换网络时（如从 WiFi 切到蜂窝），HTTP/3 连接不会中断。

HTTP/3 连接迁移场景

时刻 T1: 用户在 WiFi 下浏览
  设备 IP: 192.168.1.100
  QUIC Connection ID: 0xABCDEF
  正在下载大文件 (进度 50%)

时刻 T2: 用户走出家门，切换到 4G
  设备 IP: 10.0.0.50
  Connection ID 不变: 0xABCDEF
  
  客户端从新 IP 发送 QUIC 包
  服务器通过 Connection ID 识别
  → 文件下载继续，不中断
  → 用户无感知

对比 HTTP/2:
  TCP 连接因 IP 变化而断开
  → 文件下载失败
  → 需要重新建立连接
  → 重新请求资源

11.10.4 HTTP/3 在中国的部署挑战​

HTTP/3 在中国的部署面临特殊挑战，主要与网络基础设施相关。

挑战原因影响
UDP 限速部分运营商对 UDP 流量限速QUIC 性能下降
UDP 阻断部分企业防火墙完全阻断 UDPQUIC 不可用
QoS 差异运营商优先保障 TCP 质量UDP 延迟更高
CDN 支持国内 CDN 对 HTTP/3 支持参差不齐部署不均匀

Chrome 的智能回退机制：如果 QUIC 连接在超时内未建立，自动回退到 HTTP/2 over TCP。这使得 HTTP/3 的部署不会因为网络兼容性问题导致页面无法访问，但回退过程中会增加约 1-2 个 RTT 的延迟。

11.7 HTTP/1.1 keep-alive 与管线化​

11.7.1 keep-alive 机制​

HTTP/1.1 默认开启 keep-alive，允许在同一个 TCP 连接上发送多个请求，避免重复建立连接。

无 keep-alive（HTTP/1.0）：
  请求1 → TCP 握手 → TLS 握手 → 请求 → 响应 → 关闭
  请求2 → TCP 握手 → TLS 握手 → 请求 → 响应 → 关闭
  → 每次请求都需要完整握手

有 keep-alive（HTTP/1.1）：
  请求1 → TCP 握手 → TLS 握手 → 请求 → 响应
  请求2 → 请求 → 响应（复用连接）
  请求3 → 请求 → 响应（复用连接）
  → 只需一次握手

11.7.2 管线化及其限制​

HTTP/1.1 支持管线化（Pipelining），允许在收到前一个响应之前发送下一个请求。但管线化有严重限制：

限制说明
队头阻塞前一个响应慢，后续响应都阻塞
响应顺序必须按请求顺序返回
浏览器支持大多数浏览器默认禁用
中间件代理可能不支持

HTTP/1.1 管线化实际上几乎没人用。Chrome 和 Firefox 默认禁用管线化，因为队头阻塞问题太严重。HTTP/2 的多路复用才真正解决了 HTTP 层的队头阻塞问题。

11.8 HPACK 头部压缩​

11.8.1 HPACK 算法​

HTTP/2 使用 HPACK（Header Compression for HTTP/2，HTTP/2 头部压缩算法）压缩头部。HPACK 使用静态表、动态表和 Huffman 编码三种方式压缩。

HPACK 压缩机制

1. 静态表（61 个常见头部）
   :method: GET → 索引 2
   :path: / → 索引 4
   :scheme: https → 索引 7
   content-type: text/html → 索引 25

2. 动态表（连接级共享）
   首次发送: cookie: session=abc123
   → 存入动态表
   后续发送: cookie: session=abc123
   → 引用动态表索引

3. Huffman 编码
   对字符串值进行 Huffman 编码
   → 进一步压缩
压缩方式典型压缩率说明
无压缩0%原始大小
静态表50-70%常见头部
动态表80-95%重复头部
Huffman额外 10-20%字符串值

11.9 HTTP/2 优先级与依赖树​

HTTP/2 允许客户端为每个流设置优先级和依赖关系，指导服务器优先发送重要资源。

HTTP/2 优先级依赖树

  Root
    ├─ HTML (weight: 256, 最高优先级)
    │   ├─ CSS (weight: 200)
    │   └─ JS (weight: 100)
    ├─ Image (weight: 32)
    └─ Font (weight: 128)

  权重高的流优先分配带宽
  依赖关系决定发送顺序

HTTP/2 的优先级机制在实践中效果不佳。原因是浏览器和服务器的实现不一致，且中间代理可能忽略优先级。HTTP/3 用更简单的 Extensible Priorities 方案替代了复杂的依赖树。

11.10 0-RTT 安全风险​

11.10.1 重放攻击​

0-RTT（Zero Round Trip Time，零往返时间）允许客户端在第一次握手时就发送数据，减少延迟。但 0-RTT 数据存在重放攻击风险。

0-RTT 重放攻击场景

1. 客户端发送 0-RTT 请求（包含 POST 数据）
2. 攻击者截获请求
3. 攻击者重放请求到服务器
4. 服务器执行两次相同操作（如转账）

防护措施：
  → 服务器只允许幂等请求使用 0-RTT
  → GET/HEAD 安全，POST 不安全
  → 使用单次令牌（anti-replay token）
请求类型0-RTT 安全说明
GET安全幂等
HEAD安全幂等
POST不安全非幂等
PUT不安全非幂等
DELETE不安全非幂等

0-RTT 是性能与安全的权衡。它减少了延迟，但增加了重放攻击风险。TLS 1.3 规定 0-RTT 数据只能用于幂等请求，服务器实现必须检查请求方法。Chrome 对 0-RTT 非常谨慎，只在特定场景下使用。

11.9 HTTP/1.1 keep-alive 与管线化​

11.9.1 keep-alive 机制​

HTTP/1.1 默认开启 keep-alive，复用 TCP 连接发送多个请求。

HTTP/1.0 vs HTTP/1.1 连接

HTTP/1.0:
  连接 → 请求 → 响应 → 断开
  每次请求都建立新连接
  → TCP 握手 + TLS 握手开销大

HTTP/1.1 keep-alive:
  连接 → 请求1 → 响应1 → 请求2 → 响应2 → ... → 断开
  复用 TCP 连接
  → 节省握手开销
  → 但请求必须串行（队头阻塞）
对比HTTP/1.0HTTP/1.1 keep-alive
连接复用否是
队头阻塞无有
TCP 握手每次需要首次需要
空闲超时—Keep-Alive: timeout=5

11.9.2 管线化​

HTTP/1.1 管线化（Pipelining）允许在响应前发送多个请求，但浏览器普遍禁用了管线化。

管线化问题

1. 队头阻塞
   → 请求1响应慢 → 请求2的响应被阻塞
   → 即使请求2已处理完也要等待

2. 实现复杂
   → 服务器需要保证响应顺序
   → 中间代理可能不支持

3. 实际效果差
   → 大部分场景没有性能提升
   → 反而增加复杂度

结果：Chrome/Firefox 禁用了管线化
→ 转而使用多连接并行（6 个连接/域名）
→ HTTP/2 多路复用彻底解决了这个问题

HTTP/1.1 的队头阻塞问题是 HTTP/2 诞生的主要原因。HTTP/1.1 用 6 个并行连接缓解队头阻塞，但每个连接仍然是串行的。HTTP/2 在一个连接上多路复用多个请求，彻底消除了 HTTP 层的队头阻塞。但 TCP 层的队头阻塞仍然存在，直到 HTTP/3（QUIC）才解决。

11.10 HPACK 压缩算法​

11.10.1 HPACK 原理​

HTTP/2 使用 HPACK 算法压缩头部。HPACK 结合了静态表、动态表和 Huffman 编码。

HPACK 压缩流程

1. 静态表（61 个常见头）
   → 预定义的常用头部字段
   → 如 :method: GET → 索引 2
   → 不需要传输完整字符串

2. 动态表
   → 连接级别共享
   → 之前发送过的头部加入动态表
   → 后续请求引用索引即可

3. Huffman 编码
   → 对字符串值进行 Huffman 编码
   → 高频字符用短编码
   → 进一步压缩体积

压缩效果：
  原始头部: ~800 字节
  HPACK 后: ~30 字节
  压缩率: ~96%
压缩方式原始大小压缩后效果
无压缩800B800B0%
静态表800B400B50%
动态表800B100B87%
+ Huffman800B30B96%

HPACK 的动态表是连接级别的，不同连接不共享。这意味着首个请求的头部不会被压缩，后续请求才能命中动态表。HTTP/3 的 QPACK 改进了这一点，支持跨连接的动态表共享（需要 QUIC 的 server push 机制配合）。
