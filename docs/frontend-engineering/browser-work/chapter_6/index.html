第6章 从 HTML 到像素：渲染管线总览

当你在地址栏输入 URL 按下回车，到屏幕上出现第一像素，中间发生了什么？这条路径叫做渲染管线，它是浏览器把代码变成画面的完整流程。

我是怕浪猫，一个喜欢拆渲染管线的技术博主。前五章我们讲完了浏览器架构和 V8 引擎，今天进入第 6 章，我们正式开始拆解渲染世界。这一章会给你一个完整的渲染管线全景图：从 HTML 解析到最终像素输出，每一步干什么、怎么衔接、哪里可能成为性能瓶颈。后续几章我们会逐一深入每个环节。

6.1 渲染管线的整体流程​

6.1.1 从 HTML 到像素的完整路径​

浏览器的渲染管线（Rendering Pipeline）是将 HTML、CSS、JavaScript 转换为屏幕像素的完整流程。这个流程包含六个核心阶段。

渲染管线完整流程

HTML ──→ 解析 ──→ DOM 树
                        │
CSS  ──→ 解析 ──→ CSSOM 树
                        │
                        ▼
              样式计算（Style）
                        │
                        ▼
              布局（Layout）
                        │
                        ▼
              绘制（Paint）
                        │
                        ▼
              合成（Composite）
                        │
                        ▼
            屏幕像素（Pixels）

每个阶段的工作和输出：

阶段输入处理工作输出
HTML 解析HTML 文本构建嵌套树结构DOM 树
CSS 解析CSS 文本构建样式规则树CSSOM 树
样式计算DOM + CSSOM计算每个节点的最终样式ComputedStyle
布局DOM + ComputedStyle计算每个节点的位置和大小布局树
绘制布局树生成绘制指令列表绘制记录
合成绘制记录光栅化并合成各层像素

6.1.2 管线中各阶段的职责边界​

理解渲染管线的关键是理解每个阶段的职责边界。每个阶段有明确的输入和输出，前一阶段的输出是后一阶段的输入。

各阶段职责与触发条件

HTML 解析
  ├─ 触发：收到 HTML 数据
  ├─ 输入：HTML 字节流
  ├─ 处理：解码 → 分词 → 建树
  └─ 输出：DOM 树

CSS 解析
  ├─ 触发：遇到 <link> 或 <style>
  ├─ 输入：CSS 字节流
  ├─ 处理：解码 → 分词 → 建树
  └─ 输出：CSSOM 树

样式计算
  ├─ 触发：DOM 或 CSSOM 变化
  ├─ 输入：DOM 树 + CSSOM 树
  ├─ 处理：匹配选择器 → 计算最终值
  └─ 输出：每个节点的 ComputedStyle

布局
  ├─ 触发：DOM 结构变化或样式变化
  ├─ 输入：DOM 树 + ComputedStyle
  ├─ 处理：计算盒模型 → 排列元素
  └─ 输出：布局树（含位置和尺寸）

绘制
  ├─ 触发：布局变化或样式变化（颜色等）
  ├─ 输入：布局树
  ├─ 处理：生成绘制指令 → 分层
  └─ 输出：绘制记录列表 + 图层树

合成
  ├─ 触发：绘制完成或图层变化
  ├─ 输入：图层 + 绘制记录
  ├─ 处理：光栅化 → 合成
  └─ 输出：最终像素

渲染管线不是一条直线走到底，而是一个有反馈的流水线。JavaScript 可能在解析阶段修改 DOM，CSS 变化可能触发重新布局，动画可能让合成阶段频繁执行。理解这些交互，才能理解前端性能优化。

6.2 HTML 解析与 DOM 构建​

6.2.1 HTML 解析器的工作方式​

HTML 解析器（HTMLParser）负责将 HTML 字节流转换为 DOM 树。HTML 的解析比 XML 和 JSON 更复杂，因为 HTML 是容错的：标签可以不闭合，属性可以不加引号，标签可以嵌套错误。

HTML 解析器使用状态机（State Machine）来处理这些容错。解析器维护一个插入模式（Insertion Mode）状态，根据当前状态决定如何处理每个 Token。

HTML 解析流程

字节流（Bytes）
  │  "3C 21 44 4F 43 54 59 50 45 ..."（<!DOCTYPE...）
  ▼
字符解码（Encoding Detection）
  │  根据<meta charset>或BOM确定编码
  ▼
分词（Tokenization）
  │  状态机逐字符扫描
  │  生成 Token 序列：
  │  [StartTag html] [StartTag head] [StartTag title]
  │  [Character "Hello"] [EndTag title] ...
  ▼
建树（Tree Construction）
  │  根据 Token 和栈状态构建 DOM 节点
  │  维护一个「开放元素栈」
  ▼
DOM 树

HTML 解析器的关键特性是增量解析。解析器不需要等待整个 HTML 文件下载完毕才开始工作。网络数据到达一部分，解析器就处理一部分，构建一部分 DOM 树。这种流式处理让浏览器能在 HTML 还在下载时就开始显示页面内容。

6.2.2 预加载扫描器（Preload Scanner）​

在 HTML 解析器构建 DOM 树的同时，Chrome 还运行一个预加载扫描器（Preload Scanner）。预加载扫描器是一个轻量级的扫描器，它快速扫描 HTML 文本，寻找需要提前加载的资源（如 CSS、JavaScript、图片），不等解析器到达对应位置就提前发起网络请求。

预加载扫描器工作方式

HTML 文本流
┌──────────────────────────────────────────┐
│ <!DOCTYPE html>                          │
│ <html>                                   │
│ <head>                                   │
│   <link rel="stylesheet" href="a.css">   │ ← 预加载扫描器发现
│   <script src="b.js"></script>            │ ← 预加载扫描器发现
│   <img src="c.png">                      │ ← 预加载扫描器发现
│ </head>                                  │
│ <body>                                   │
│   <script src="d.js"></script>            │ ← 预加载扫描器发现
│ </body>                                  │
└──────────────────────────────────────────┘

预加载扫描器在解析器还在 <head> 时
就已经发现了 c.png 和 d.js，提前发起请求

预加载扫描器的价值在于减少资源加载的串行等待。没有预加载扫描器，浏览器必须等解析器到达 <img> 标签时才能开始加载图片。有了预加载扫描器，图片的请求可以在解析器还在处理 head 部分时就已经发出。

6.2.3 DOM 树的数据结构​

DOM（Document Object Model，文档对象模型）树是 HTML 解析的输出，也是后续渲染管线的基础数据结构。

DOM 树结构示例

HTML:
  <div id="container">
    <p>Hello</p>
    <span>World</span>
  </div>

DOM 树:
  Document
    └── html
          ├── head
          └── body
                └── div#container
                      ├── p
                      │   └── #text "Hello"
                      └── span
                            └── #text "World"

DOM 树中的每个节点都是一个对象，包含标签名、属性、子节点列表、父节点引用等信息。V8 和 Blink 共同维护 DOM 树：Blink 负责 DOM 的 C++ 实现，V8 负责将 DOM 对象暴露给 JavaScript。

6.3 CSS 解析与 CSSOM​

6.3.1 CSS 解析过程​

CSS 解析器将 CSS 文本转换为 CSSOM（CSS Object Model，CSS 对象模型）树。与 HTML 解析不同，CSS 解析不需要容错，CSS 语法规则严格。

CSS 解析流程

CSS 文本
  │  body { color: red; }
  │  p { font-size: 16px; }
  ▼
词法分析（Tokenizer）
  │  生成 Token 序列
  ▼
语法分析（Parser）
  │  构建 CSSOM 树
  ▼
CSSOM 树

CSSOM 树的结构反映了 CSS 选择器的层级关系。每个节点包含样式规则和子规则。

6.3.2 CSSOM 树与样式继承​

CSSOM 树的一个重要特性是样式继承（Inheritance）。某些 CSS 属性（如 color、font-size）会从父元素继承到子元素。继承在 CSSOM 树构建时就确定了，不需要在样式计算阶段逐级查找。

属性类别是否继承示例
文本属性是color、font-size、line-height
盒模型属性否width、height、margin、padding
定位属性否position、top、left
背景属性否background-color、background-image
可见性是visibility、cursor

6.4 关键渲染路径​

6.4.1 阻塞渲染的资源​

并非所有资源都会阻塞渲染。理解哪些资源阻塞渲染，是优化首次渲染的关键。

资源阻塞规则

HTML ──── 解析阻塞（自身）
  │
  ├── <link rel="stylesheet"> ── 渲染阻塞（必须等 CSS 加载完）
  │                              不阻塞 DOM 解析
  │
  ├── <script src="..."> ────── 解析阻塞（必须等 JS 加载执行完）
  │                           阻塞 DOM 解析
  │
  ├── <script async> ──────── 不阻塞（异步加载，加载完执行）
  │                           不阻塞 DOM 解析
  │
  ├── <script defer> ──────── 不阻塞（异步加载，DOM 解析完后执行）
  │                           不阻塞 DOM 解析
  │
  └── <img> ──────────────── 不阻塞（异步加载）
资源类型阻塞 DOM 解析？阻塞渲染？说明
CSS否是必须等 CSS 加载完才渲染
普通 script是是加载和执行都阻塞解析
script async否短暂加载不阻塞，执行时短暂阻塞
script defer否否DOM 解析完后执行
图片否否完全异步

6.4.2 FOUC（Flash of Unstyled Content）​

如果浏览器在 CSS 加载完成前就渲染了页面，用户会看到没有样式的 HTML 内容，这叫做 FOUC（Flash of Unstyled Content，无样式内容闪烁）。

Chrome 的策略是：在 CSS 加载完成前，阻塞渲染（但不阻塞 DOM 解析）。这意味着浏览器会继续解析 HTML 构建 DOM，但不会把内容画到屏幕上，直到 CSSOM 构建完成。

渲染阻塞时序

时间轴：
  t0: HTML 开始下载
  t1: HTML 部分到达，开始解析 DOM
  t2: 发现 CSS link，发起 CSS 请求
  t3: HTML 全部到达，DOM 解析完成
  t4: ---- 等待 CSS ----
  t5: CSS 到达，CSSOM 构建完成
  t6: 样式计算 → 布局 → 绘制 → 首次渲染

  t3 到 t6 之间：DOM 已就绪但渲染被 CSS 阻塞

CSS 是渲染阻塞资源，但这不是缺陷而是特性。没有这个阻塞，用户会看到样式闪烁。优化方向不是消除阻塞，而是让 CSS 尽快加载完（如内联关键 CSS）。

6.5 渲染管线的性能特征​

6.5.1 重新渲染的触发条件​

页面不是只渲染一次的。用户交互、JavaScript 修改 DOM、CSS 动画等都会触发重新渲染。重新渲染的范围决定了性能影响。

重新渲染的三种级别

1. 重排（Reflow / Layout）
   触发：DOM 结构变化、尺寸变化、位置变化
   范围：布局 → 绘制 → 合成
   代价：高

2. 重绘（Repaint）
   触发：颜色、背景色、阴影等外观变化
   范围：绘制 → 合成
   代价：中

3. 合成（Composite Only）
   触发：transform、opacity 变化
   范围：合成
   代价：低
渲染级别触发条件管线阶段性能代价
重排尺寸、位置、结构变化Layout → Paint → Composite高
重绘外观变化（颜色等）Paint → Composite中
合成transform、opacityComposite低

这就是为什么前端性能优化推荐用 CSS transform 做动画而非修改 top/left：transform 只触发合成阶段，跳过了布局和绘制，性能最优。

6.5.2 渲染频率与帧率​

浏览器以帧（Frame）为单位进行渲染。理想情况下每秒渲染 60 帧（60fps），每帧的预算约 16.6ms。如果一帧的渲染时间超过 16.6ms，就会出现掉帧（Jank）。

一帧 16.6ms 的时间分配

┌────────────────────────────────────────┐
│              一帧（16.6ms）              │
│                                        │
│  ┌──────────┐  ┌─────────┐  ┌────────┐│
│  │ JavaScript│  │ 渲染管线 │  │  合成  ││
│  │ 执行      │  │Style+   │  │ 输出   ││
│  │           │  │Layout+  │  │ 像素   ││
│  │           │  │Paint    │  │        ││
│  └──────────┘  └─────────┘  └────────┘│
│  约 5-8ms       约 5-8ms     约 2-4ms  │
└────────────────────────────────────────┘

如果 JS 执行 + 渲染管线 + 合成 > 16.6ms
→ 掉帧，用户感觉卡顿

6.5.3 requestAnimationFrame 的作用​

requestAnimationFrame（rAF）是浏览器提供的 API，用于在下一次渲染前执行回调。它确保回调在一帧的正确时机执行，避免渲染和 JS 执行的冲突。

rAF 执行时序

帧 N:
  JS 执行 → rAF 回调 → Style → Layout → Paint → Composite
                                                        │
帧 N+1:                                                │
  JS 执行 → rAF 回调 → Style → Layout → Paint → Composite

rAF 的关键价值是同步动画与渲染。如果你在 rAF 回调中修改样式，浏览器会在同一帧内完成样式计算和渲染，不会出现「修改了样式但本帧没渲染」的问题。

动画方式执行时机与渲染同步性能
setTimeout不确定否差
setInterval不确定否差
requestAnimationFrame下一次渲染前是好

16.6ms 不是给你写 JavaScript 的时间，而是 JavaScript + 样式计算 + 布局 + 绘制 + 合成的总时间。你的 JS 只能占其中一部分，通常不超过 5-8ms。

6.5.4 帧率检测与 PerformanceObserver​

开发者可以通过 PerformanceObserver API 监控帧率，识别掉帧情况。Chrome 提供了 "long animation frame"（长动画帧）的观测能力，帮助开发者发现超过 50ms 的渲染帧。

// 监控长动画帧
const observer = new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    console.log('Long frame:', entry.duration, 'ms');
    console.log('Scripts:', entry.scripts);
  }
});
observer.observe({ type: 'long-animation-frame', buffered: true });

这种监控方式可以在线上环境持续运行，帮助发现真实用户遇到的渲染卡顿问题。

6.5.5 渲染管线的并行与异步​

现代 Chrome 渲染管线并非严格的串行流程，而是尽可能并行执行。样式计算和布局计算在主线程上串行执行，但合成阶段在独立的合成器线程上执行，光栅化在工作线程上并行执行。

这种并行设计让主线程可以开始下一帧的 JavaScript 执行和样式计算，同时合成器线程在处理上一帧的合成输出。当主线程因为 JavaScript 执行而卡住时，合成器线程仍然可以处理滚动和 CSS transform 动画，保持流畅的用户体验。

6.6 Blink 渲染引擎在 Chrome 中的位置​

Blink 是 Chrome 的渲染引擎，负责从 HTML 解析到合成的全部工作。Blink 运行在渲染进程中，与 V8 引擎紧密协作。

Blink 在 Chrome 架构中的位置

┌─────────────────────────────────┐
│         Renderer 进程            │
│                                 │
│  ┌───────────┐ ┌─────────────┐ │
│  │   Blink    │ │     V8      │ │
│  │           │ │            │ │
│  │ DOM/CSSOM │ │ JavaScript │ │
│  │ Layout    │ │ 执行        │ │
│  │ Paint     │ │            │ │
│  │ Composite │ │            │ │
│  └─────┬─────┘ └──────┬─────┘ │
│        │              │       │
│        └──── 绑定层 ───┘       │
│        (DOM API 桥接)          │
│                               │
│  ┌───────────────────────────┐│
│  │     Compositor 线程        ││
│  │  (合成器，独立于主线程)     ││

        │ IPC

6.6 JIT 编译的触发条件与热点检测​

6.6.1 Profiler 与热点检测​

V8 如何知道哪些代码是「热点代码」需要 JIT 编译？这依赖于 Profiler（性能分析器）的持续监控。

V8 的 Profiler 是一个轻量级的采样分析器，它在 Ignition 解释执行时持续收集类型反馈（Type Feedback）信息。每次属性访问、函数调用、算术运算都会被记录。当某个函数的调用次数达到预设阈值时，Profiler 会触发对应层级的编译器。

V8 热点检测与触发阈值

函数调用次数          触发的编译器
──────────────────────────────────────
0-9 次          →    Ignition (解释执行)
                      收集类型反馈
10-99 次        →    Sparkplug (非优化编译)
                      快速生成机器码
100-999 次      →    Maglev (中层优化)
                      部分优化
1000+ 次        →    TurboFan (顶层优化)
                      激进优化

阈值不是固定的，V8 会根据函数大小和复杂度动态调整。小函数的阈值更低（更容易被优化），大函数的阈值更高（避免编译开销过大）。

6.6.2 类型反馈的收集与使用​

类型反馈是 JIT 编译的核心输入。Ignition 在解释执行时，会为每个关键操作记录类型信息。

// 类型反馈收集示例

function process(items) {
  let sum = 0;
  for (let i = 0; i < items.length; i++) {
    sum += items[i];
  }
  return sum;
}

// 第一次执行 process([1, 2, 3])
// Ignition 记录:
//   items 的类型: PACKED_SMI_ARRAY
//   items[i] 的类型: Smi (小整数)
//   sum 的类型: Smi
//   += 操作: NumberAdd

// 前几百次都传整数数组
// 类型反馈稳定: 都是 Smi

// TurboFan 编译时:
//   假设 items 始终是 PACKED_SMI_ARRAY
//   假设元素始终是 Smi
//   生成特化的整数加法循环
//   消除所有类型检查和边界检查(部分)

类型反馈存储在 FeedbackVector 中，每个函数都有一个关联的 FeedbackVector。FeedbackVector 是一个固定大小的数组，每个槽位对应一个类型反馈点。

6.6.3 函数内联优化​

内联（Inlining）是 TurboFan 最强大的优化之一。它将函数调用替换为函数体的内联副本，消除调用开销并开启更多优化空间。

// 内联前
function double(x) { return x * 2; }
function process(arr) {
  let sum = 0;
  for (let i = 0; i < arr.length; i++) {
    sum += double(arr[i]);  // 每次迭代有函数调用开销
  }
  return sum;
}

// TurboFan 内联后 (概念)
function process(arr) {
  let sum = 0;
  for (let i = 0; i < arr.length; i++) {
    sum += arr[i] * 2;  // double 被内联，函数调用消除
    // 后续优化: 循环展开、向量化等
  }
  return sum;
}

内联的决策因素：函数大小（小函数更容易内联）、调用频率（频繁调用的函数优先内联）、是否在热循环中（循环内的函数调用影响最大）、内联后的代码膨胀程度（不能无限内联）。

TurboFan 的内联策略是递归的：内联一个函数后，如果被内联的函数也调用了其他小函数，那些函数也会被内联。这种递归内联可以深入多层，但有深度和代码膨胀的限制。

6.6.4 逃逸分析​

逃逸分析（Escape Analysis）是 TurboFan 的高级优化。它分析对象是否「逃逸」出当前函数——如果对象只在函数内部创建和使用，没有被返回或传递给外部，V8 可以避免在堆上分配它。

// 不逃逸的对象
function calculate(x, y) {
  const point = { x: x, y: y };  // 创建对象
  return point.x + point.y;       // 只在函数内使用
}

// 逃逸分析后 (标量替换):
function calculate(x, y) {
  // point 对象被拆解为两个标量
  const point_x = x;
  const point_y = y;
  return point_x + point_y;  // 无堆分配
}

// 逃逸的对象 (无法优化)
function createPoint(x, y) {
  const point = { x: x, y: y };
  return point;  // 对象逃逸到外部
  // 必须在堆上分配
}

逃逸分析的收益：避免堆分配（减少 GC 压力）、消除对象访问开销（标量直接在寄存器中）、为后续优化（如常量折叠）创造条件。

6.6.5 图着色寄存器分配​

TurboFan 在生成机器码时需要做寄存器分配——决定哪些变量放在 CPU 寄存器中，哪些放在内存中。寄存器是有限的资源（x64 只有 16 个通用寄存器），需要智能分配。

图着色寄存器分配（Graph Coloring Register Allocation）是一种经典的算法。它将变量之间的冲突关系建模为图：如果两个变量在同一时刻活跃（都需要被访问），它们之间有一条边。然后用图着色算法为图中的节点分配颜色（寄存器），相邻节点不能同色。

图着色寄存器分配 (简化)

变量活跃分析:
  代码: a = 1; b = 2; c = a + b; d = c * 2;
  
  a 活跃区间: [语句1, 语句3]
  b 活跃区间: [语句2, 语句3]
  c 活跃区间: [语句3, 语句4]
  d 活跃区间: [语句4, ...]

冲突图:
  a --- b  (同时活跃)
  b --- c  (同时活跃)
  a --- c  (同时活跃)
  c --- d  (同时活跃)

着色 (假设3个寄存器 R1, R2, R3):
  a = R1, b = R2, c = R3, d = R1
  (a 和 d 不冲突，可以复用 R1)

6.6.6 JIT 与 AOT 对比​

JIT（即时编译）和 AOT（Ahead-Of-Time，提前编译）是两种不同的编译策略，各有优劣。

维度JIT (V8)AOT (Java GraalVM, Go)
编译时机运行时运行前
类型信息有运行时类型反馈只有静态类型
启动速度快 (先解释)慢 (需提前编译)
峰值性能高 (基于实际类型优化)中 (无法利用运行时信息)
内存占用高 (保存多份代码)低
预热期有无

JIT 的核心优势是「基于运行时信息的优化」。它知道哪些代码是热点，知道变量的实际类型，可以做出 AOT 无法做到的推测优化。但代价是预热期和内存占用。

6.6.7 V8 各编译器的优化层级与切换条件​

V8 编译器切换条件

执行次数      编译器      优化级别      切换条件
───────────────────────────────────────────────
0            Ignition    无 (解释)     函数首次调用
~10          Sparkplug   无 (直译)     调用次数 ≥ threshold_1
~100         Maglev      部分          调用次数 ≥ threshold_2
~1000        TurboFan    激进          调用次数 ≥ threshold_3

反优化:
TurboFan → Ignition (类型变化)
Maglev → Ignition (类型变化)
Sparkplug → Ignition (罕见)

重新优化:
Ignition → Sparkplug → Maglev → TurboFan
(基于新的类型反馈)

切换条件不是硬编码的固定值，V8 会根据多种因素动态调整：函数大小、调用频率、类型反馈的稳定性、内存压力等。在内存紧张时，V8 可能不触发 TurboFan 编译以节省内存。在性能模式下（如游戏场景），V8 可能降低阈值更快地触发优化。

V8 的四层编译管道是一个精密的梯度优化系统。每一层都在「编译成本」和「执行性能」之间找到不同的平衡点。理解这个梯度，就能理解为什么 V8 启动后越来越快，以及为什么某些代码模式会导致性能不稳定。

6.5 JIT 触发条件与热点检测​

6.5.1 Profiler 热点检测​

V8 不会立即优化所有代码，而是通过 Profiler 检测热点代码（Hot Code）后再优化。这避免了为只执行一次的代码浪费编译资源。

热点检测流程

1. 代码首次执行 → Ignition 解释执行
2. Profiler 采样计数器
   → 每次执行函数，计数器 +1
   → 函数执行超过阈值（约 1000 次）→ 标记为热点
3. 热点代码 → 提交给 TurboFan 优化
4. 非热点代码 → 继续解释执行
编译层级触发条件目标
Ignition默认快速启动
SparkPlug函数被调用多次减少解释开销
Maglev热点函数中等优化
TurboFan极热点函数最大化优化

Profiler 使用采样而非精确计数，以减少性能开销。采样频率约 1ms 一次，记录调用栈。这意味着短时间执行的函数可能不会被检测到，而长时间运行的函数会更快被优化。

6.6 函数内联优化​

6.6.1 内联原理​

TurboFan 会将小函数内联到调用处，消除函数调用开销并暴露更多优化机会。

// 优化前
function add(a, b) { return a + b; }
function calculate(x) { return add(x, 10) * 2; }

// TurboFan 内联后（等价于）
function calculate_optimized(x) { return (x + 10) * 2; }
内联决策因素

1. 函数大小
   → 小函数（< 600 字节）优先内联
   → 大函数不内联

2. 调用频率
   → 热点调用优先内联

3. 是否有 try-catch
   → try-catch 中的函数不内联

4. 是否有 eval/with
   → 包含 eval/with 不内联

内联是 JIT 最强大的优化之一。它不仅消除了函数调用开销，更重要的是将多个函数的代码合并，让编译器看到更完整的上下文，进行更深入的优化（如常量折叠、死代码消除）。

6.7 逃逸分析​

6.7.1 逃逸分析原理​

逃逸分析（Escape Analysis）判断对象是否「逃逸」出函数。未逃逸的对象可以分配在栈上而非堆上，减少 GC 压力。

// 未逃逸：对象只在函数内部使用
function process() {
  const temp = { a: 1, b: 2 };  // 不逃逸
  return temp.a + temp.b;
}
// TurboFan：不分配堆对象，直接用寄存器

// 逃逸：对象被返回或传递到外部
function create() {
  const obj = { a: 1, b: 2 };  // 逃逸
  return obj;  // 返回给调用者
}
// TurboFan：必须在堆上分配
逃逸类型说明优化
不逃逸只在函数内部使用栈分配 / 标量替换
方法逃逸被作为参数传递堆分配
线程逃逸被其他线程访问堆分配

标量替换（Scalar Replacement）是逃逸分析的进一步优化。未逃逸的对象不分配在栈上，而是将对象的字段直接替换为局部变量，完全消除对象分配。例如 {a:1, b:2} 变成两个局部变量 a=1, b=2。

6.8 JIT 与 AOT 对比​

对比项JIT（V8）AOT（C/C++）
编译时机运行时编译时
启动速度慢（需要预热）快
峰值性能接近 AOT最优
代码体积小（源码）大（二进制）
类型信息运行时收集编译时已知
反优化可能发生不存在

JIT 的核心优势是「运行时类型反馈」。V8 在运行时收集类型信息，基于实际运行数据进行优化。AOT 没有这个优势，但也不会出现反优化。JIT 的峰值性能已经接近 AOT（通常在 70-90% 之间），但在某些边界场景（如类型频繁变化）可能退化。
