# 第3章 V8 引擎概览

> 你写的 JavaScript 代码，V8 引擎不是一行一行翻译的，而是经过一条精密的编译管道，最终变成 CPU 能直接执行的机器码。这条管道上有 6 个关卡，每个关卡都在决定你的代码能跑多快。

我是怕浪猫，一个喜欢拆引擎的技术博主。上期讲完 Chrome 的多进程架构，今天我们进入 V8 引擎的世界。这一章会完整拆解 V8 的执行管道，从源代码到机器码的每一步，以及 V8 的内存管理和垃圾回收机制。这是整个系列最硬核的几章之一，做好准备。

## 3.1 V8 的设计目标与核心思想

V8 是 Google 为 Chrome 浏览器开发的 JavaScript 引擎，于 2008 年随 Chrome 一起发布。它的名字来源于那台著名的 V8 发动机，暗示的是高性能。

V8 的核心设计目标只有一个：让 JavaScript 的执行速度尽可能接近原生代码。这在 2008 年是一个非常激进的目标，因为当时的 JavaScript 引擎（如 SpiderMonkey、JScript）普遍采用解释执行，速度比编译型语言慢 1-2 个数量级。

V8 实现这个目标依赖三个核心思想。

### 3.1.1 JIT 编译：为什么需要即时编译

JIT（Just-In-Time Compilation，即时编译）是 V8 最核心的技术。要理解 JIT 的价值，先看看两种传统执行方式的优劣。

| 执行方式 | 工作原理 | 优点 | 缺点 |
|---------|---------|------|------|
| 解释执行 | 逐行解析源代码，直接执行 | 启动快，内存占用低 | 运行慢 |
| AOT 编译 | 运行前将源代码全部编译为机器码 | 运行快 | 启动慢，内存占用高 |
| JIT 编译 | 运行时监控热点代码，编译为机器码 | 启动快，运行快 | 实现复杂，有预热开销 |

JIT 的核心思想是「边执行边优化」。代码开始以解释方式快速启动执行，同时引擎监控哪些函数被频繁调用（热点代码）。当某个函数被调用足够多次后，JIT 编译器会将它编译为优化的机器码，后续调用直接执行机器码。

```
JIT 编译工作流程
源代码
  │
  ▼
解释执行（快速启动）
  │  监控执行频率和类型信息
  │  函数调用次数 > 阈值？
  │
  ├── 否 ── 继续解释执行
  │
  └── 是 ── JIT 编译器介入
              │
              ▼
          生成优化机器码
              │
              ▼
          后续调用直接执行机器码（性能接近原生）
```

JIT 编译的关键优势是它利用了运行时信息。传统 AOT（Ahead-Of-Time，提前编译）编译在运行前就完成，无法知道代码的实际运行模式。JIT 在运行时收集信息，知道哪些代码是热点、变量通常是什么类型，可以据此做更激进的优化。

> JIT 不是「解释和编译的二选一」，而是「先解释再编译，用运行时信息指导优化」的聪明策略。它让 JavaScript 既有快速启动，又有高速运行。

### 3.1.2 隐藏类（Hidden Classes / Shapes）

JavaScript 是动态类型语言，对象的属性可以随时增删，类型可以随时变化。这让属性访问的优化变得非常困难。

在静态类型语言（如 C++、Java）中，对象的内存布局在编译时就确定了。访问一个属性就是简单的内存偏移计算，只需要一条机器指令。而 JavaScript 中，对象的属性随时可能变化，无法在编译时确定内存布局。

V8 的解决方案是隐藏类（Hidden Classes），也叫 Shapes 或 Maps。隐藏类是 V8 在对象背后维护的一个描述对象「形状」的数据结构。

```
隐藏类工作原理

// 创建对象
let p1 = { x: 1, y: 2 };

// V8 内部状态：
// p1 的隐藏类 HC1 描述：有属性 x（偏移0）和 y（偏移1）
// 访问 p1.x → 通过 HC1 查找，x 在偏移0 → 直接读取内存

// 创建另一个同形状对象
let p2 = { x: 3, y: 4 };

// V8 发现 p2 的形状与 p1 相同
// p2 复用同一个隐藏类 HC1
// 访问 p2.x → 同样通过 HC1 查找 → 同样读取偏移0
```

当对象的属性发生变化时，V8 会创建一个新的隐藏类，并与旧的隐藏类建立转换链接：

```
隐藏类转换链

对象 p = { x: 1 }
  → 隐藏类 HC0 { x: offset 0 }

p.y = 2  (添加属性 y)
  → 隐藏类 HC1 { x: offset 0, y: offset 1 }
  (HC0 → HC1 的转换链接：添加属性 y)

p.z = 3  (添加属性 z)
  → 隐藏类 HC2 { x: offset 0, y: offset 1, z: offset 2 }
  (HC1 → HC2 的转换链接：添加属性 z)
```

隐藏类的关键性能影响：如果多个对象的属性添加顺序相同，它们会共享相同的隐藏类，属性访问会很快。如果属性添加顺序不同，会创建不同的隐藏类，导致性能下降。

| 代码模式 | 隐藏类行为 | 性能 |
|---------|-----------|------|
| `p1 = {x:1, y:2}; p2 = {x:3, y:4}` | p1 和 p2 共享同一隐藏类 | 好 |
| `p1 = {x:1, y:2}; p2 = {y:4, x:3}` | p1 和 p2 有不同隐藏类 | 差 |
| `p1 = {}; p1.x=1; p1.y=2;` | 逐步添加，创建多个隐藏类 | 一般 |
| `p1 = {}; delete p1.x` | 删除属性导致隐藏类变化 | 差 |

> 隐藏类是 V8 让动态语言拥有静态语言属性访问速度的秘密武器。代价是开发者必须注意属性的添加顺序，否则隐藏类会碎片化。

### 3.1.3 内联缓存（Inline Caches）

内联缓存（Inline Caches，IC）是与隐藏类配合的另一项核心优化技术。

当 V8 执行属性访问 `obj.x` 时，它会记录上一次访问时 obj 的隐藏类和属性 x 的偏移量。下次再执行同一段代码时，如果 obj 的隐藏类没变，就直接用上次记录的偏移量访问属性，跳过隐藏类查找过程。

```
内联缓存工作原理

第一次执行 obj.x：
  1. 查找 obj 的隐藏类 → HC1
  2. 在 HC1 中查找 x → 偏移量 0
  3. 读取 obj+0 的值
  4. 缓存信息：(HC1, x → offset 0)

第二次执行 obj.x：
  1. 检查 obj 的隐藏类 → HC1 (与缓存一致)
  2. 直接读取 obj+0 (跳过查找)
  3. 完成（比第一次快很多）
```

内联缓存有几种状态，随着代码执行的深入逐步变化：

| IC 状态 | 含义 | 性能 |
|--------|------|------|
| Uninitialized | 首次执行，未缓存 | 最慢 |
| Monomorphic | 缓存了一种隐藏类 | 快 |
| Polymorphic | 缓存了 2-4 种隐藏类 | 中等 |
| Megamorphic | 超过 4 种隐藏类，放弃缓存 | 慢 |

> 内联缓存和隐藏类是 V8 性能优化的「双子星」。隐藏类让属性有固定的位置，内联缓存让访问跳过查找。两者配合，动态语言的属性访问可以接近静态语言的性能。

## 3.2 V8 的执行管道（Execution Pipeline）

V8 的执行管道是理解 V8 工作原理的核心。从 JavaScript 源代码到 CPU 执行的机器码，中间经过多个阶段，每个阶段都有不同的编译器负责。

### 3.2.1 解析阶段（Parsing）：Scanner 与 Parser

JavaScript 代码在 V8 中的第一步是解析。解析分为两个子阶段：词法分析（Scanning）和语法分析（Parsing）。

Scanner（词法分析器）的工作是将源代码字符串分解为 Token（词法单元）。例如：

```
源代码：let x = 1 + 2;

Scanner 输出：
  Token: LET
  Token: IDENTIFIER "x"
  Token: EQUALS
  Token: NUMBER 1
  Token: PLUS
  Token: NUMBER 2
  Token: SEMICOLON
```

Parser（语法分析器）接收 Token 流，根据 JavaScript 语法规则构建 AST（Abstract Syntax Tree，抽象语法树）。AST 是源代码的树形结构表示，每个节点代表一个语法结构。

```
AST 结构示例

源代码：let x = 1 + 2;

AST：
  VariableDeclaration
  ├── name: "x"
  └── init: BinaryExpression
            ├── operator: "+"
            ├── left: Literal (value: 1)
            └── right: Literal (value: 2)
```

### 3.2.2 AST 生成与预解析（Preparse / Lazy Parsing）

V8 的解析策略不是一次性解析所有代码，而是采用懒解析（Lazy Parsing）策略。

JavaScript 代码中经常有大量函数定义但未必会被调用。如果一开始就把所有函数都完整解析为 AST，会浪费大量时间和内存。V8 的策略是：

```
预解析与完整解析

// 顶层代码：立即完整解析
function outer() {           // 预解析（只看结构，不生成完整 AST）
  var x = 1;                 //
  function inner() {         // 预解析
    return x + 1;            //
  }                          //
  return inner();            // outer 被调用时，完整解析 outer 函数体
}                            //
                             // inner 被调用时，完整解析 inner 函数体
```

预解析（Preparse）只做最基本的语法检查，记录函数的参数名和变量名，不生成完整的 AST。当函数被实际调用时，才进行完整解析。

这种策略的好处：

| 策略 | 首次解析时间 | 内存占用 | 适用场景 |
|------|------------|---------|---------|
| 全量解析 | 慢 | 高 | 所有代码都执行 |
| 预解析 + 懒解析 | 快 | 低 | 大部分代码不执行 |

> 预解析是 V8 用空间换时间的反向操作：用「不完全解析」换「更快的启动」。对于大型 Web 应用，预解析可以节省数百毫秒的启动时间。

### 3.2.3 Ignition 解释器（字节码执行）

Ignition 是 V8 的解释器，它接收 Parser 生成的 AST，将其编译为字节码（Bytecode），然后逐条解释执行。

字节码是一种中间表示，比源代码更紧凑，比机器码更抽象。每条字节码指令对应一个操作，如加载变量、算术运算、函数调用等。

```
Ignition 字节码示例

JavaScript 源代码：
  function add(a, b) {
    return a + b;
  }

生成的字节码（简化版）：
  Lda a          // 将参数 a 加载到累加器
  Star r0        // 将累加器值存入寄存器 r0
  Lda b          // 将参数 b 加载到累加器
  Add r0         // 将 r0 的值与累加器相加
  Return         // 返回累加器的值
```

Ignition 的字节码是平台无关的，同一份字节码可以在任何平台上运行。字节码的执行速度比源代码解释快，但比机器码慢。Ignition 同时承担一个关键职责：收集类型反馈（Type Feedback）信息，为后续的 JIT 编译提供优化依据。

### 3.2.4 Sparkplug 编译器（非优化中间层）

Sparkplug 是 V8 在 2021 年引入的编译器，位于 Ignition 和 TurboFan 之间。它的角色是「非优化编译器」。

为什么要加一个非优化编译器？因为 Ignition 解释执行虽然启动快，但对于频繁执行的代码，解释开销仍然显著。而 TurboFan 优化编译虽然运行快，但编译时间长，需要等待足够的类型反馈数据。

Sparkplug 填补了这个空档：

```
V8 编译管道（含 Sparkplug）

源代码 → AST → Ignition 字节码
                        │
                        ▼
                   Ignition 解释执行（收集类型反馈）
                        │  函数调用 ~10 次
                        ▼
                   Sparkplug 编译（非优化机器码，快速生成）
                        │  函数调用 ~1000 次
                        ▼
                   TurboFan 编译（优化机器码，基于类型反馈）
```

Sparkplug 编译速度极快（比 TurboFan 快两个数量级），生成的代码虽然不优化，但比解释执行快 50% 左右。

| 编译阶段 | 编译速度 | 执行速度 | 触发条件 |
|---------|---------|---------|---------|
| Ignition（解释） | 极快 | 慢 | 立即 |
| Sparkplug | 快 | 中等 | 调用约 10 次 |
| TurboFan | 慢 | 快 | 调用约 1000 次 |

### 3.2.5 Maglev 编译器（中层优化 JIT）

Maglev 是 V8 在 2023 年引入的编译器，位于 Sparkplug 和 TurboFan 之间。它是中层优化编译器，填补了 Sparkplug 和 TurboFan 之间的性能空档。

Maglev 的设计目标是：比 Sparkplug 更优化，但编译速度比 TurboFan 快得多。它利用 Ignition 收集的类型反馈做部分优化，但不做 TurboFan 那么激进的优化。

```
V8 完整编译管道（2024 版）

Ignition（解释器）
  │  收集类型反馈
  ▼
Sparkplug（非优化编译器）
  │  快速生成机器码
  ▼
Maglev（中层优化编译器）
  │  基于类型反馈做中等优化
  ▼
TurboFan（顶层优化编译器）
     基于类型反馈做激进优化
```

四层编译管道让 V8 可以根据代码的热度逐步提升优化级别，在启动速度和峰值性能之间取得平衡。

| 编译器 | 角色 | 优化程度 | 编译速度 | 执行速度 |
|--------|------|---------|---------|---------|
| Ignition | 解释器 | 无 | 极快 | 慢 |
| Sparkplug | 非优化编译 | 无 | 快 | 中等 |
| Maglev | 中层优化 | 部分 | 中等 | 快 |
| TurboFan | 顶层优化 | 激进 | 慢 | 很快 |

> 四层编译管道不是过度设计，而是 V8 团队 15 年优化的结晶。每一层都在「编译时间」和「执行性能」之间找到不同的平衡点，让代码从冷启动到热运行的每一步都有最优选择。

### 3.2.6 TurboFan 编译器（顶层优化 JIT）

TurboFan 是 V8 的顶层优化编译器，它基于 Ignition 收集的类型反馈信息，生成高度优化的机器码。

TurboFan 的主要优化策略：

| 优化策略 | 说明 | 效果 |
|---------|------|------|
| 类型特化 | 根据类型反馈，假设变量类型不变，生成特化代码 | 消除类型检查 |
| 内联 | 将被调用函数的代码嵌入调用处 | 消除调用开销 |
| 逃逸分析 | 分析对象是否逃逸出函数，未逃逸的对象分配在栈上 | 减少堆分配 |
| 边界检查消除 | 根据循环分析，消除冗余的数组边界检查 | 减少分支 |
| 常量折叠 | 编译期计算常量表达式 | 减少运行时计算 |

### 3.2.7 反优化（Deoptimization）

JIT 编译的一个根本假设是「历史行为预测未来行为」。如果这个假设被打破（例如变量的类型发生了变化），V8 必须执行反优化（Deoptimization）。

反优化是将 TurboFan 生成的优化机器码回退到 Ignition 字节码执行的过程。

```
反优化触发示例

function process(x) {
  return x + 1;
}

// 前 1000 次调用都传数字
process(1);   // TurboFan 假设 x 始终是数字
process(2);   // 编译为：直接整数加法
...
process(999);

// 第 1001 次调用传入字符串
process("hello");  // 类型假设被打破！
              // → 触发反优化
              // → 回退到 Ignition 字节码执行
              // → 后续可能重新触发 TurboFan（以新类型）
```

反优化的代价很高：不仅要回退到解释执行，还要丢弃优化代码，后续可能需要重新编译。频繁的反优化会严重拖慢性能。

> 反优化是 JIT 编译的「安全网」。没有它，类型假设出错会导致错误的结果。但频繁触犯反优化等于在编译和解编译之间来回折腾，性能反而不如纯解释执行。

## 3.3 V8 的内存管理

### 3.3.1 堆（Heap）结构划分

V8 将 JavaScript 对象存储在堆（Heap）中，堆被划分为多个区域，每个区域有不同的管理策略。

```
V8 堆结构
┌─────────────────────────────────────────┐
│                  V8 Heap                 │
│                                         │
│  ┌───────────────────────────────────┐  │
│  │         新生代（Young Gen）         │  │
│  │  ┌───────────┐ ┌───────────┐     │  │
│  │  │ From-Space │ │ To-Space  │     │  │
│  │  │ (活跃对象)  │ │ (空闲)    │     │  │
│  │  └───────────┘ └───────────┘     │  │
│  └───────────────────────────────────┘  │
│                                         │
│  ┌───────────────────────────────────┐  │
│  │         老生代（Old Gen）           │  │
│  │  ┌──────────┐ ┌────────────────┐  │  │
│  │  │ 指针空间  │ │ 数据空间        │  │  │
│  │  │(含指针对象)│ │(纯数据对象)     │  │  │
│  │  └──────────┘ └────────────────┘  │  │
│  └───────────────────────────────────┘  │
│                                         │
│  ┌───────────┐ ┌───────────┐           │
│  │大对象空间  │ │ 代码空间   │           │
│  │(Large Obj)│ │(Code Space)│          │
│  └───────────┘ └───────────┘           │
└─────────────────────────────────────────┘
```

各区域的职责：

| 区域 | 存储内容 | GC 策略 | 大小 |
|------|---------|---------|------|
| 新生代 | 新创建的对象 | Scavenge（复制式） | 较小（1-8MB） |
| 老生代 | 存活时间长的对象 | Mark-Sweep-Compact | 较大 |
| 大对象空间 | 超过阈值的大对象 | 独立管理 | 按需分配 |
| 代码空间 | JIT 生成的机器码 | 独立管理 | 中等 |

### 3.3.2 垃圾回收机制

#### 3.3.2.1 Minor GC（Scavenge / Cheney 算法）

新生代的垃圾回收使用 Scavenge 算法，基于 Cheney 的半空间复制策略。

新生代被分为两个相等的半空间：From-Space 和 To-Space。新对象分配在 From-Space 中。当 From-Space 满了时，触发 Scavenge：

```
Scavenge 工作流程

回收前：
  From-Space: [A] [B] [C] [D] [E] [F]  (部分存活，部分垃圾)
  To-Space:   (空)

回收过程：
  1. 从根集合遍历，标记存活对象
  2. 将存活对象从 From-Space 复制到 To-Space
  3. 复制过程中整理内存，消除碎片

回收后：
  From-Space: (空)
  To-Space:   [A] [C] [E]  (仅存活对象，紧凑排列)

交换 From-Space 和 To-Space
```

Scavenge 的优点是速度快（只处理存活对象，不扫描垃圾），缺点是浪费一半内存空间。对于新生代中「大多数对象朝生夕灭」的特点，这个策略非常高效。

在 Scavenge 过程中，如果某个对象已经经历过一次 Scavenge（即已经存活了一次 GC），它会被晋升（Promote）到老生代。

#### 3.3.2.2 Major GC（Mark-Sweep-Compact / Orinoco）

老生代的垃圾回收使用 Mark-Sweep-Compact（标记-清除-整理）算法，由 Orinoco 项目实现并发和增量优化。

三个阶段的工作：

```
Major GC 三阶段

阶段一：标记（Mark）
  从根集合出发，遍历对象引用链
  标记所有可达对象为「存活」
  
  根集合包括：
  - 全局对象
  - 当前执行栈中的局部变量
  - 寄存器中的引用

阶段二：清除（Sweep）
  遍历堆中所有对象
  未被标记的对象即为垃圾，释放其内存

阶段三：整理（Compact）
  将存活对象向内存一端移动
  消除内存碎片
  更新引用地址
```

| 阶段 | 工作 | 耗时 | 暂停主线程？ |
|------|------|------|------------|
| 标记 | 遍历引用链，标记存活对象 | 长 | 部分（可并发） |
| 清除 | 扫描堆，释放垃圾对象内存 | 中 | 短暂 |
| 整理 | 移动对象，消除碎片 | 长 | 短暂 |

#### 3.3.2.3 并发标记与并行清理

Orinoco 项目对 Major GC 的关键优化是并发标记（Concurrent Marking）。标记阶段可以在后台线程执行，不阻塞主线程。

```
并发标记工作模型

主线程：    [JavaScript 执行] ──┬── [JavaScript 执行] ──┬── [短暂暂停]
                              │                        │
辅助线程：                    └── [并发标记] ───────────┘
                              (标记阶段大部分在后台完成)
```

并发标记的难点在于：主线程在执行 JavaScript 时可能修改对象引用关系，导致标记结果不一致。V8 通过写屏障（Write Barrier）解决：当主线程修改引用关系时，通过写屏障通知 GC 线程更新标记状态。

#### 3.3.2.4 增量标记与空闲时间垃圾回收

增量标记（Incremental Marking）将一次长时间的标记任务拆分为多个小步骤，穿插在 JavaScript 执行之间。每个步骤只标记一小部分对象，然后交还控制权给主线程。

空闲时间垃圾回收（Idle-Time GC）利用浏览器空闲时间执行 GC。当 Chrome 知道下一帧渲染还有空闲时间时，会通知 V8 执行一部分 GC 工作。

| GC 优化策略 | 原理 | 效果 |
|------------|------|------|
| 并发标记 | 标记阶段在后台线程执行 | 减少主线程暂停 |
| 增量标记 | 标记拆分为小步骤 | 缩短单次暂停时间 |
| 空闲时间 GC | 利用空闲时间执行 GC | 避免影响交互 |
| 并行清理 | 多线程同时清理 | 加速清理阶段 |

> 现代 GC 的核心目标不是「更快回收」，而是「更少暂停」。V8 的 Orinoco 项目把 GC 暂停从几十毫秒降到几毫秒，让 Web 应用几乎感受不到 GC 的存在。

### 3.3.3 内存泄漏的常见模式

即使有 GC，JavaScript 仍然可能发生内存泄漏。内存泄漏的本质是：对象不再使用，但仍然被引用，导致 GC 无法回收。

常见内存泄漏模式：

| 模式 | 原因 | 示例 |
|------|------|------|
| 意外的全局变量 | 变量未声明就赋值 | `function f() { x = 1; }` |
| 被遗忘的定时器 | setInterval 未清理 | `setInterval(() => {...}, 1000)` |
| 闭包引用 | 闭包持有大对象引用 | 闭包中引用了不需要的大数组 |
| DOM 引用 | JS 变量引用已移除的 DOM | `let el = document.getElementById('x'); el.remove();` |
| 事件监听器 | 未移除的监听器 | `addEventListener` 无对应 `removeEventListener` |

## 3.4 Mojo 的 IDL 定义与代码生成

### 3.4.1 Mojo IDL 语法详解

Mojo 使用自己的接口定义语言（IDL）来描述进程间通信的接口。IDL 文件以 `.mojom` 为扩展名，定义了消息类型、数据结构和接口方法。

```
// navigation.mojom (简化示例)

// 定义一个结构体
struct NavigationParams {
  url.mojom.Url url;
  string method;
  array<uint8> post_body;
  bool is_reload;
};

// 定义一个接口
interface NavigationHost {
  // 异步方法：请求导航
  RequestNavigation(NavigationParams params) => (bool success);
  
  // 异步方法：通知导航完成
  DidFinishNavigation(bool success, string error_message);
  
  // 同步方法（阻塞调用方）
  [Sync] GetCookies(string url) => (string cookies);
};

// 定义枚举
enum NavigationType {
  kReload,
  kHistory,
  kNewNavigation,
};
```

Mojo IDL 支持多种数据类型，包括基本类型（int32, float, bool 等）、字符串、数组、映射、嵌套结构体和接口指针。每个 `.mojom` 文件会被代码生成器编译为多种语言的绑定代码。

### 3.4.2 代码生成流程

Mojo 的代码生成器接收 `.mojom` 文件，生成对应语言的接口实现代码。Chrome 主要使用 C++ 绑定，但也支持 JavaScript 和 Java 绑定。

```
Mojo 代码生成流程

navigation.mojom
       │
       ▼
  Mojo 编译器 (mojom_parser)
       │  语法分析 + 语义检查
       ▼
  代码生成器 (generators)
       │
       ├─► C++ 生成
       │   ├─ navigation.mojom.h        (接口声明)
       │   ├─ navigation.mojom-internal.h (内部实现)
       │   └─ navigation.mojom.cc        (实现代码)
       │
       ├─► JavaScript 生成
       │   └─ navigation.mojom-web.js    (JS 绑定)
       │
       └─► Java 生成
           └─ NavigationHostMojom.java   (Java 绑定)
```

生成的 C++ 代码包含：接口基类（定义纯虚方法）、代理类（Stub，用于发送 IPC 消息）、实现绑定（实现具体业务逻辑）、序列化/反序列化代码（将参数编码为二进制消息）。

### 3.4.3 ChannelProxy 与消息管道

Mojo 的底层通信依赖 ChannelProxy。ChannelProxy 是一个平台无关的 IPC 通道抽象，它在不同平台上使用不同的底层传输机制。

```
ChannelProxy 架构

应用层          Mojo Interface (类型安全)
                       │
               MessagePipe (双向消息管道)
                       │
                 ChannelProxy
                       │
          ┌────────────┴────────────┐
          │                         │
    序列化/反序列化           消息路由
          │                         │
    ┌─────┴─────┐           ┌──────┴─────┐
    │ Linux     │           │ 跨进程      │
    │ Unix      │           │ 消息传递    │
    │ Domain    │           │ (FD passing)│
    │ Socket    │           │            │
    └───────────┘           └────────────┘
```

在 Linux 上，Mojo 使用 Unix Domain Socket 作为底层传输。Unix Domain Socket 支持传递文件描述符（FD passing），这让 Mojo 可以高效地传递共享内存的句柄。在 macOS 上使用 Mach Port，在 Windows 上使用 Named Pipe。

### 3.4.4 序列化与反序列化机制

Mojo 的消息在传输前需要序列化为二进制格式。Mojo 使用自定义的高效序列化格式，而非 Protocol Buffers 或 JSON。

```
Mojo 消息序列化

原始调用:
  navigation_host->RequestNavigation(params)
  params = { url: "https://example.com", method: "GET" }

序列化后的二进制消息:
┌────────────────────────────────────────┐
│ Message Header                        │
│  ├─ message_id: 0x1234                │
│  ├─ interface_id: 0x0001              │
│  └─ flags: async                      │
├────────────────────────────────────────┤
│ Payload (序列化后的 NavigationParams)   │
│  ├─ url: "https://example.com"        │
│  │   (length-prefixed string)          │
│  ├─ method: "GET"                     │
│  │   (length-prefixed string)          │
│  └─ is_reload: false                  │
│      (1 byte bool)                    │
└────────────────────────────────────────┘
```

Mojo 序列化的特点是对齐优化：所有字段按自然对齐方式排列，避免填充浪费。指闹和字符串使用偏移量引用，支持结构体嵌套和循环引用。整个序列化过程不涉及任何内存分配（在预分配的缓冲区上操作），性能极高。

### 3.4.5 IPC 安全验证（Trusted/Untrusted）

并非所有 IPC 消息都是可信的。渲染进程可能被恶意网页攻破，因此从渲染进程发来的 IPC 消息必须经过严格验证。

Chrome 将 IPC 消息分为两类：受信任的（Trusted）和不受信任的（Untrusted）。受信任的消息来自浏览器进程自身或其他可信进程，不受信任的消息来自渲染进程。

```
IPC 消息验证层次

第1层：消息格式验证
  ├─ 消息大小是否合法？
  ├─ 字段偏移是否在范围内？
  ├─ 字符串长度是否合理？
  └─ 嵌套深度是否超限？

第2层：语义验证
  ├─ 调用者是否有权限调用此接口？
  ├─ URL 是否合法？
  ├─ 文件路径是否在允许范围内？
  └─ 权限检查是否通过？

第3层：内容验证
  ├─ URL 是否属于恶意站点？
  ├─ 请求频率是否异常？
  └─ 数据大小是否超限？
```

每个 Mojo 接口在注册时会声明其安全级别。渲染进程只能调用被标记为「渲染进程可调用」的接口方法。例如，渲染进程可以请求导航到新 URL，但不能直接读取文件系统。

### 3.4.6 跨进程序调用的实现

Mojo 支持 [Sync] 标记的同步方法。同步方法会阻塞调用方进程，直到被调用方返回结果。这看起来简单，但实现上需要处理死锁和重入问题。

```
同步调用流程

渲染进程 A                    浏览器进程 B
    │                              │
    │  [Sync] GetCookies(url)      │
    │ ────────────────────────────►│
    │                              │
    │  (A 阻塞等待响应)             │  处理请求...
    │                              │  读取 Cookie 数据库
    │                              │
    │  ←───────────────────────────│
    │  (cookies)                   │
    │                              │
    │  A 恢复执行                   │
```

同步调用的问题在于：如果被调用方也需要回调调用方（重入），就会死锁。Mojo 通过「同步调用时继续处理其他异步消息」来部分解决这个问题。调用方在等待响应时，仍然会处理收到的其他异步 IPC 消息，但不会处理同步消息。

### 3.4.7 消息优先级与调度

并非所有 IPC 消流都是同等重要的。用户输入事件（如鼠标点击、触摸）需要尽快处理，而后台任务的消息可以延迟。Mojo 支持消息优先级机制。

```
Mojo 消息优先级

优先级队列：
  ┌────────────────────────────┐
  │ 最高：用户输入事件           │  ← 立即处理
  │  ├─ touchmove, click       │
  │  └─ keydown                │
  ├────────────────────────────┤
  │ 高：渲染相关                 │  ← 下一帧前处理
  │  ├─ requestAnimationFrame  │
  │  └─ 合成器更新              │
  ├────────────────────────────┤
  │ 中：默认                     │  ← 尽快处理
  │  ├─ 网络响应                │
  │  └─ 定时器回调              │
  ├────────────────────────────┤
  │ 低：后台任务                 │  ← 空闲时处理
  │  ├─ requestIdleCallback    │
  │  └─ 数据预取                │
  └────────────────────────────┘
```

Chrome 的任务调度器在 IO 线程上接收所有 IPC 消息，根据优先级放入不同队列。高优先级队列中的消息会被优先分派到目标线程处理。这种设计确保了即使在大量后台 IPC 消息涌入时，用户交互仍能获得快速响应。
